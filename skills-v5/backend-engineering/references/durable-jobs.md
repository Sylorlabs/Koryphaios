# Durable jobs and external side effects

Read when the requested backend accepts work that may be retried or redelivered, has competing workers, or performs effects outside its transactional state store. A queue, database, and object store are possible components, not required architecture.

## Commit and ownership model

1. Identify the caller's existing accepted/result/status/error contract, the namespace and lifetime of request idempotency keys, the durable job identity, and whether a reused key with different content is a conflict. Scope identity to the actual caller or tenant and operation; a payload hash alone cannot distinguish two intended identical submissions. The first accepted payload owns the authoritative record. A retry with the same key and equivalent content returns the existing supported result. A retry with the same key and different content follows the existing conflict contract; when the preserved public contract has no conflict response, return that existing result without replacing the original payload or silently accepting the second intent. Preserve current public semantics while making each logical submission resolve to one authoritative record. Keep the recorded intent and result long enough for the permitted retry horizon, including late retries after completion or deletion.
2. Use a durable uniqueness constraint or atomic compare and set at the state owner for registration and state transitions. Treat a lookup local to the process followed by an insert as racy. Persist intent before asynchronous dispatch; if storage and queue cannot commit together, use an existing outbox or a recoverable publication step. Publishing and delivery may repeat. Acknowledge delivery only after the result or recoverable intent is durable; redelivery after a commit must resolve to the existing state.
3. When workers compete, claim work atomically. Where a claim can expire, define the authority for expiry and protect completion, renewal, and release with an ownership generation or fencing token so a resumed stale worker cannot overwrite the newer result. Coordinate any external effect separately: a database claim does not fence an object store or a remote API.
4. Identify exactly what an interruption can leave behind: uploaded object without completed job, committed result before queue acknowledgment, canceled job with active work, or an expired claim still executing. Define how cancellation races a durable effect under the existing contract. Prefer stable object identity and supported conditional/idempotent writes where available; otherwise define reconciliation or cleanup. Do not report an external side effect as exactly once unless the external boundary enforces it. The same stable object key is an identity and reconciliation aid, not proof of exclusive ownership or exactly once delivery.
5. A timeout may hide a completed effect. Reconcile by the stable operation identity before repeating it. Bound admission, retries, and failed work retention, and preserve a recoverable terminal or quarantine state for poison work. If cleanup or compensation is required, persist its progress and make it repeatable; it can fail too. Condition deletion on the artifact identity or generation it owns so a stale cleanup cannot delete a newer valid result.

## Evidence that distinguishes a correct implementation

Exercise the existing caller contract with duplicate submissions using the same key, reuse of a key with a different payload when relevant, and preservation of the original payload or documented conflict result. Inject a failure immediately before and after a durable transition and between an external effect and its record or acknowledgment. Restart using the real persisted state; replay messages, let an old claim try to finish, and verify one logical job result, consistent external artifacts, and compatible statuses. Include cancellation and bounded retry or poison work behavior when those transitions exist. Report effects that cannot be proven or safely repeated instead of masking them with a successful retry. If the adapter only makes synchronous calls against state held in memory, label competing claims, durable restart, lease fencing, and queue acknowledgment as unavailable; do not turn sequential replay into a concurrency claim.

See [the source map](sources.md) for retry identity, overload, isolation, and compensation guidance. Provider conditional writes, queue acknowledgment, and lease semantics still require the actual adapter's versioned contract.
