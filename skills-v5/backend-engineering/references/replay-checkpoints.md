# Checkpoints that replay safely

Read when a backend consumes a paged feed, applies local changes, and resumes from a cursor or checkpoint. The same reasoning applies to a local daemon or a sync loop inside the process; neither requires a new database server or network service.

## Align replay with effects

1. Inspect the feed's documented ordering, stable change identity, opaque cursor semantics, replay/retention window, and invalid or expired cursor behavior. Inspect the current consumer API and local transaction capabilities. Never derive an opaque next cursor from record count or assume that advancing it acknowledges partially applied pages.
2. Define the invariant: a checkpoint only covers changes whose **logical effects** are durably applied or explicitly accounted for as no effect under the feed contract. If restart can replay a page, deduplicate every replayable change against a persistent journal of applied IDs or equivalent atomic guard, scoped to its source and owner. Pair that guard with **all** local effects in the same transaction where possible; idempotent entity upserts alone do not prevent duplicated counters, notifications, or other effects that are not idempotent. Distinguish entity identity from change identity; two changes to one entity are not duplicates. Reject stale versions before adding logical effects when that is the consumer contract.
3. Commit a page's next cursor only after all its effects are accounted for. If the cursor update fails, replay the page safely from the previous checkpoint; if the process stops partway through, resume without skipping uncommitted records. For effects outside the local transaction, use a durable intent/outbox plus sink idempotency or reconciliation, and describe any unavoidable duplicate window.
4. Serialize overlapping sync runs or guard the effects, deduplication, and checkpoint together with the expected checkpoint or ownership generation. A conditional cursor write alone cannot stop a losing run's earlier effects. Compare opaque tokens for equality only; use an owned local generation if ordering is needed. Cancellation must stop at a safe commit boundary. Retain deduplication identities for at least the actual replay horizon, accounting for cursor expiry and recovery policy.
5. An empty page can still have a continuation; stop only on the feed's documented terminal signal. Preserve deletion or tombstone semantics so old updates cannot resurrect deleted data. For expired cursors, stage and validate the documented resync or reconciliation path before replacing local state; do not silently skip to the latest cursor, erase unsynced user changes, or replay historical side effects as new work. If there is no stable change identity, require another enforceable replay guard or report the effect guarantee as unavailable.

## Restart and compatibility proof

For a representative feed with multiple pages, inject interruption after each applied record, before and after a page checkpoint, and after the final page. Reopen a fresh process or store instance using persisted state, replay stale and duplicate changes (including duplicates on another page), and verify exact entity state, counters or external side effects, final cursor, and an unchanged supported consumer contract. A successful second fetch or matching entity rows alone does not prove that side effects were applied once. State feed guarantees or recovery paths that the fixture/runtime cannot exercise.

See [the source map](sources.md) for concrete opaque token, replay, empty page, and reset examples. Microsoft Graph delta responses describe entity state and do not supply a universal stable change ID; do not infer an event journal contract from that API.
