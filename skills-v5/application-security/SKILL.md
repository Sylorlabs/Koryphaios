# Application Security

Trace data and privilege that the attacker controls through the real runtime. For every entry point, identify the first trusted interpretation, sensitive sinks, the invariant enforced before each sink, and behavior that fails closed. Earlier validation is not proof if later decoding, canonicalization, deserialization, or interpolation changes meaning.

For implementation tasks, secure the smallest complete path through the affected sinks and run focused existing tests as soon as that path is changed. Once the required implementation and relevant tests pass, **finish the turn promptly** with concise verification evidence. Do not spend the remaining execution budget on optional refactoring, repeated checks, lengthy prose, or speculative dependency installation; label unavailable optional checks rather than trying to fetch missing tools. If the task requires a source-to-sink map or other documentation, write a concise map before testing and extend it only when needed to substantiate a required control. A complete, verified result delivered within the task budget is part of successful hardening. Preserve the recorded call shape of every control you harden: a synchronous guard stays synchronous and returns its decision value directly, because existing callers and tests read that return value (a guard that becomes `async` hands them a `Promise` and every assertion about its result breaks), and an asynchronous one stays asynchronous. If the call shape genuinely must change, update every caller in the same change and say so.

## Secure design workflow

1. **Map sources, assets, and sinks.** Include APIs/network, files/archives, IPC/deep links, imports/clipboard, config/environment, stored values later reinterpreted, queues/plugins, and responses from third parties. Mark secrets, user data, privileged operations, filesystem/process/network access, and durable state.
2. **Trace interpretation end to end.** Follow values through decode/normalize/parse/transform/store/reuse into queries, templates, command arguments, paths, URL fetchers, deserializers/interpreters, logs, and privileged APIs.
3. **Parse narrowly and canonically.** Bound serialized bytes before buffering/parsing and bound parser work before schema validation; checks after parsing cannot prevent parser exhaustion. Prefer typed/schema parsing with explicit size/count/range/enumeration limits when the application actually defines those constraints; reject forms that violate that real contract. Canonicalize where identity matters, then enforce policy on the canonical value. Keep semantic validation separate from sink escaping: do not reject otherwise valid data merely because punctuation would be dangerous in a different sink, and do not invent a new semantic allowlist just to make a sink feel safer.
4. **Use sink-safe APIs.** Parameterize queries; avoid shell interpolation; encode for the actual rendering context; constrain outbound schemes/hosts/resolved destinations; enforce normalized archive/path containment plus resource limits. For subprocesses, use structured argv to an identified executable, then inspect its option and operand semantics: avoiding a shell does not prevent argument injection. Separate data from options with documented mechanisms such as `--` where supported. Derive permitted effects from the actual application and tool contract. Explicitly authorized option passthrough can remain valid within its trust and resource boundary; unknown option semantics are an unresolved risk, not proof of safe opaque data. Do not invent business validation or reject valid punctuation merely to satisfy a fixture.
   For outbound fetches, trace supplied URL → parsed authority/userinfo → redirects/retries → DNS answers → actual connected destination → response bytes. Apply the application's scheme, authority, and network policy at every hop; reject credential-bearing URL userinfo unless the interface explicitly supports it. Ensure the transport connects only to a validated address (or an equivalently enforced destination), retaining the intended TLS hostname and certificate checks. A successful DNS precheck followed by an unchecked lookup is not enforcement. Do not forward sensitive headers across untrusted redirect origins. Exercise a permitted destination, credential-bearing URL, private-address redirect, and changed DNS/connected-peer negative case; distinguish an actual unsafe destination from an otherwise permitted public test address.
5. **Bound resource abuse.** Cap body/file/archive size, nesting/decompression, object counts, recursion, time, memory, redirects, response/output size, subprocess count, and diagnostic volume where those resources exist. When the task explicitly requires concrete limits but the product has no configured values, do not leave the contract at “bounded” or “finite”: choose explicit conservative provisional ceilings, label them as proposed rather than observed policy, keep them configurable where appropriate, and verify that exceeding them fails closed. Multiple decoding passes and parser differentials are security-relevant.
6. **Protect session and sensitive state.** Define create/renew/invalidate/expire/revoke semantics, reauthentication for sensitive actions, and safe token/secret storage. Keep secrets out of logs, crash reports, URLs, analytics, and user-facing errors. Treat secrecy as a data-classification property rather than a single field-name regex: access credentials, refresh credentials, bearer/API tokens, authorization material, cookies/session identifiers, recovery material, and application-specific aliases remain sensitive after relabeling, flattening, serialization, or conversion to free-form diagnostic text. Derive the sensitive-name vocabulary from the actual data model and transformations, including shortened or serialized aliases such as bare `refresh`, `auth`, `sid`, and `jwt` labels; do not require a `token`, `key`, or `secret` suffix before protecting a value that is semantically a credential. Prefer structured allowlisted diagnostics that never receive secret values. Where unstructured third-party/error text must be retained, redact complete credential-bearing syntaxes such as `Authorization: Bearer <credential>` before broader field-name substitutions, and ensure an earlier replacement cannot leave a trailing credential fragment that later rules miss. Treat credentials separated by a newline, space, delimiter, or encoded boundary as independently sensitive. Redact common equivalent representations before persistence or display, then strip unsafe control content and bound the result. Verify redaction with multiple credential classes, bare aliases, and at least one full authorization-header form rather than one sample key.
7. **Keep denial without effects.** Invalid input must not partially mutate state or fall through to privileged defaults. Revalidate persisted commands and authority at restoration and execution; reject or quarantine corrupt state explicitly according to its contract instead of silently treating it as valid empty state. Return bounded safe errors without unsafe reflection.
8. **Make state-changing paths logically once.** Where an operation can be retried, redelivered or interrupted, key it on a stable logical identity that the caller supplies or the application derives from the request, and make the second attempt reuse the first result instead of repeating its side effects: a duplicate submission must not replace the stored payload or enqueue a second delivery, a redelivery after the commit must be a no-op, repeated cancellation must stay terminal and must not revive queued work, and recovery after a crash mid-operation must reconcile to exactly one committed output. Persist the identity and the decision next to the effect so it survives a restart; an in-memory set of seen identifiers loses the guarantee at exactly the moment it matters. Report duplicate detection as the operation's normal result, so a caller can tell a benign retry from a real failure.

For filesystem authority, compare the canonical target against the canonical allowed root using path components, including absolute inputs and symlink resolution. An absolute path is never its own authorization. For a new target, resolve existing ancestors and constrain creation without following an escaping link; do not invent nonexistent absolute roots for tests.

## Evidence and review handoff

Produce the map from sources to sinks and trust, sink invariants, resource limits, session contract, and negative cases. `security-review` owns broader finding synthesis; `security-verification` independently proves finished controls.

Retain executable regressions for the repaired trust crossings, including a permitted control, a rejected input and recovery after partial work. Preserve existing security regression coverage and extend it for each repaired boundary; do not delete or replace maintained tests unless equivalent coverage is demonstrably retained. Assert that denial creates no privileged effect, secrets and terminal controls stay out of persisted diagnostics, and failed staging or persistence leaves a recoverable state. Include cleanup and restoration observations in the handoff; implementation changes alone do not provide that evidence.

## Boundaries

- `authorization-security`: subject/resource/action/field/tenant policy. `secure-authentication`: authenticator/login/recovery/reauth assurance. `web-security`: browser-origin/XSS/CSRF/CSP/CORS/framing/cookie/postMessage rules. `language-runtime-security`: untrusted-code runtimes/sandboxes. `security-review`: finding quality/severity. `security-verification`: final runtime proof.
