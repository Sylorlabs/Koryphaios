# AI safety evaluation source map

Verified 2026-09-05. This package treats official standards/project guidance as the factual boundary and research/community benchmarks as patterns to adapt, not universal truth. Re-check fast-moving risk taxonomies, model-provider guidance, and evaluation frameworks before making current-product claims.

## Evaluation implementations and research patterns

| Source                                                                                | Type / provenance                                                         | Pattern worth adopting                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [UK AI Security Institute Inspect AI](https://github.com/UKGovernmentBEIS/inspect_ai) | Reference implementation; MIT; verify current main/release within 30 days | Explicit task datasets, tool-using/multi-turn trajectories, reusable scorers, sandboxing, logs, and separable evaluation components. Reproducible configuration and raw artifacts matter as much as the headline score.                                                        |
| [HarmBench](https://arxiv.org/abs/2402.04249)                                         | Research/community pattern                                                | Standardize target behaviors and scoring enough to compare attacks/defenses; evaluate robustness across multiple attack methods and target configurations rather than one hand-written jailbreak. Do not copy its harm taxonomy blindly into a deployment-specific risk model. |
| [AgentDojo](https://arxiv.org/abs/2406.13352)                                         | Research/community pattern                                                | For tool-using agents, combine realistic benign tasks with adversarial indirect-prompt-injection cases and measure both security and utility. A defense that blocks attacks by making the agent useless is not a successful system-level mitigation.                           |

## Interpretation rules

- **Claim before benchmark.** Decide whether the result is meant to support a capability claim, a safeguard-robustness claim, or a deployment-behavior claim. The correct harness and adversary budget depend on that choice.
- **System identity is part of the result.** Record model/revision, prompts, tools, permissions, memory/retrieval, safeguards, harness, retries, and resource budget when they can affect behavior. Do not report a system result as an intrinsic property of a base model.
- **Threat-model before attack catalog.** OWASP and ATLAS provide coverage ideas; select only scenarios reachable under the actual product boundary and attacker prerequisites.
- **Safety and utility are separate axes.** Pair adversarial cases with benign controls. Report attack success, allowed-task success/false refusal, severity, prerequisites, and attempts/cost separately rather than averaging them into one score.
- **Prefer observable state.** Use deterministic checks for tool calls, secret/canary disclosure, permissions, state transitions, and task completion. Use semantic graders for genuinely semantic judgments and calibrate them against labeled examples or blind review.
- **Preserve validity hazards.** Broken tasks, contamination, scorer/reward hacking, refusal artifacts, evaluator leakage, and evaluation awareness can invalidate a result. Keep raw traces and document exclusions/adjustments.
- **Regression is mandatory after mitigation.** Re-run the same adversarial and benign cases after prompt/model/policy/tool/permission/filter changes. Preserve confirmed failures as permanent regression cases until the failure mode is retired with evidence.
- **Keep red teaming authorized and bounded.** Use synthetic/canary targets and isolated environments where practical. Do not expand an evaluation request into unauthorized access or publish sensitive operational attack details outside the approved audience.
