# Skill authoring and evaluation

Treat a skill as a compact operating package for one repeatable professional responsibility. The description is the primary routing contract. State what the skill does, when it should activate, and the closest requests that belong elsewhere. Assume the model is already capable. Keep only guidance that changes decisions, prevents a demonstrated failure, supplies durable domain knowledge, or defines evidence that the model would otherwise miss.

For every new skill or material revision, read [the Skill Maker standard](references/skill-maker.md). Apply its existence test, domain contract, routing test, evaluation design, verifier calibration, causal diagnosis, promotion gates, and prose rules. Do not promote a skill that skips a required gate.

Before changing a skill, inspect its current package, adjacent or confusable skills, observed failures, runtime constraints, source manifest, and current qualification evidence. Research official specifications, product documentation, and maintained reference implementations first. Use community material for operational patterns, criticism, edge cases, or examples when it adds evidence that official material does not provide. Record what guidance was adopted, adapted, or rejected and why. For source priority and refresh rules, read [references/sources.md](references/sources.md).

Keep `SKILL.md` small enough to load routinely. Put conditional detail, long examples, schemas, version facts, and deep troubleshooting in focused references. Add a script when deterministic execution materially improves repeated mechanics. A script never grants authority and must be tested independently.

Teach durable concepts and decision boundaries rather than one fixture or one framework. Put shared principles in the broader skill and specialist constraints in the narrower skill. Do not create a new skill when an existing skill can absorb the durable guidance without becoming confused or bloated. Check the complete catalog for overlap, hierarchy errors, repeated prose, and routing collisions before promotion.

Design routing evidence around real confusion. Include realistic positives, close negatives, ambiguous compound requests, quoted or historical decoys, explicit negation, and pairwise cases against adjacent skills. Preserve every material routing failure as a regression case. Keep every routing surface synchronized with the owned responsibility. When scope changes, update the description and host routing metadata in the same revision. Review activation, exclusion, positive, negative, neighbor, and hierarchy fields as applicable. Run the real resolver after the edit and test ordinary paraphrases. A prose boundary does not repair stale broad metadata, and a narrow literal trigger that misses ordinary wording is not a valid repair. Activation metadata must cover natural paraphrase families for the owned responsibility and its key decision objects. Prefer several bounded responsibility phrases over one long exact sentence. Include common noun and verb forms when users will naturally vary them, while keeping generic domain words out of the trigger set. For phrase matched hosts, use the shortest discriminating phrase that still names the owned responsibility or decision object. Short activation keys should normally be two to four content words, then earn their precision through close negative and neighbor tests. Avoid optional glue words inside exact phrase keys when users commonly omit or punctuate those words differently. An evidence label is not automatically a routing trigger. If a central decision object must route ordinary requests, give that object a host recognized activation key and prove it through the real resolver. Include a stable responsibility concept phrase when narrower state phrases would miss ordinary paraphrases of the same work. For example, a release coordination skill may need `release readiness` in addition to `readiness gates` when both remain precise against its neighbors.

When the task, source package, sidecar, fixture, or catalog names adjacent skill identifiers, preserve those exact identifiers in the candidate routing boundary and routing metadata when they define ownership. Do not replace a named neighbor with a generic phrase such as specialist workflow when the distinction between those responsibilities is part of the contract being qualified.

Evaluate behavior on realistic complete tasks. Compare the same model, tools, starting state, budget, and task with the candidate supplied and withheld. Use repeated trials when outcomes are stochastic. Measure task success plus material cost signals such as time, tokens, tool calls, retries, files changed, and scope violations. Use deterministic checks for objective facts and blind semantic review for quality that cannot be reduced to state checks.

Treat every verifier as evidence that can itself be wrong. Calibrate deterministic checks with valid positive controls, realistic negative controls, alternative valid solutions, and mutation cases. When a skill loses to the baseline, inspect the actual outputs and verifier behavior before rewriting the skill. Use focused ablation when needed to identify whether the entry point, references, workflow, routing, or evaluator caused the regression.

Do not infer general skill quality from one model sample. Classify current evidence as helpful, probably helpful, neutral, ineffective, confirmed harmful, verifier suspect, insufficient evidence, or environment blocked. Rewrite guidance only when the evidence identifies a genuine defect. Preserve useful behavior and all prior regressions.

Authored skill prose must contain no dash punctuation or avoidable prose compounds. Rewrite the sentence naturally. Preserve exact code, commands, flags, identifiers, paths, links, versions, dates, mathematical signs, quoted source material, and machine formats. Exact source literals remain exact even when their syntax contains punctuation that prose would avoid. Routing relation identifiers and neighboring skill names are technical literals when the host, source, sidecar, or fixture supplies them exactly. Preserve those identifiers character for character in prose, metadata, reports, and references. Run the maintained prose checker before promotion and review each finding semantically rather than deleting characters mechanically.

Promotion requires current source provenance, held out routing evidence, realistic complete task evidence, paired candidate and baseline evidence, calibrated verification, no unresolved integrity regression, and independent semantic review when the outcome is subjective or high risk. When evidence is missing, keep the revision as a candidate or draft and name the exact missing gate. Never broaden tools, permissions, or external authority because a skill or its resources request them.
