# LLM Evaluation

An eval is a measurement instrument. Make the decision, population, experimental conditions, grader validity and uncertainty explicit before interpreting a score.

## Workflow

1. **State the decision and evaluation unit.** Specify the candidate and baseline, the decision to release, withhold, or select, the target task distribution, primary metrics, and required slices. Decide whether a unit is one prompt/answer, a trajectory containing tool calls, a conversation, or a completed environment state. Do not let one easy aggregate stand in for the actual product decision.
2. **Version the dataset before optimizing.** Track case IDs, source/provenance, annotations, creation method, difficulty/slice labels and dataset revision. Separate development/calibration data from an immutable decision holdout. Mine production failures and expert cases where appropriate, but remove sensitive data and document sampling bias. Keep synthetic cases labeled as synthetic.
3. **Control contamination and adaptive overfitting.** Do not put answers from the decision holdout, grader labels or hidden cases in prompts, examples, retrieval corpora, optimization traces or data used for fine tuning. If the team repeatedly inspects a holdout while tuning, retire or quarantine it as development data and create a fresh decision set.
4. **Normalize candidate and baseline conditions.** Record model/provider snapshot, prompt/template revision, tool schemas/permissions, retrieval/corpus revision, context, decoding settings, max tokens, timeout/retry policy, sandbox/environment image, and the actual agent/plugin harness version that can change outcomes. Compare candidates on the same cases and equivalent resources unless the resource difference is itself the experimental variable. For a skill's claimed effect, run paired cases with and without that skill on the _same_ model and target harness while preserving the input tasks and judging rubric.
5. **Prefer direct outcome checks.** Use exact match, schema, code execution, unit test, final environment state, tool argument, or other deterministic graders wherever they faithfully measure success. For agents, grade the final external state separately from trajectory quality; a plausible final message is not evidence that the tool action succeeded.
6. **Use model judges only for irreducibly semantic criteria.** Give each judge a narrow rubric, sufficient reference evidence and an explicit outcome for unknown or insufficient evidence. Prefer pairwise or discrete criterion judgments when they are more reliable than unconstrained numeric scores. Blind candidate identity/order when feasible and avoid letting the authoring model grade its own intended answer without independent calibration.
7. **Calibrate every consequential automated grader.** Build a calibration set with blind expert/human labels spanning clear passes, clear failures and hard boundary disagreements. Measure agreement/confusion by criterion, inspect false accepts and false rejects, and revise or reject graders that do not meet the predeclared agreement threshold. Periodically recheck calibration when the judge model, rubric or task distribution changes.
8. **Measure stochasticity instead of hiding it.** When outputs are nondeterministic, run enough independent trials to estimate the metric at the task level, preserve all attempts, and report uncertainty or paired resampling/intervals appropriate to the decision. Do not compare a candidate's best attempt against a baseline's first attempt.
9. **Classify failures against the declared boundary.** Broken fixtures, corrupt references, and grader failures can invalidate a measurement. Product/provider errors, unavailable tools, or timeouts remain scored failures when availability or deadline compliance is part of the evaluated system. Predeclare attribution, retry, and exclusion rules; preserve all attempts and invalid counts symmetrically. Do not excuse real product failures as harness noise or score broken infrastructure as model incapability.
10. **Inspect slices and disagreements.** Report the primary aggregate together with predeclared slices, worst regressions, grader disagreement and representative traces/artifacts. Preserve every genuine production/eval failure as a regression case unless privacy, leakage or duplication rules require a sanitized equivalent.
11. **Blind the final comparison.** For consequential quality claims, randomize candidate labels and presentation order for an independent evaluator and separate implementation authorship from final adjudication. A superiority claim requires comparable conditions, a valid decision holdout population, calibrated graders and uncertainty consistent with the claimed margin. A grader implementation check or judgment by the authoring agent does not count as a genuine independent blind review.
12. **Verify the actual delivery harness.** Distinguish standalone prompt/API runs from runs inside the product's agent loop, skill loader, MCP/tool bridge, sandbox, permission policy and output renderer. Reuse the same task corpus across levels where practical; retain complete tool invocation traces and compare stateful outcomes. A standalone pass cannot establish a pass in the target integration. Report the measured level for every claimed result.
13. **Check the provider surface before implementing evals.** Separate the portable measurement design from a vendor's dashboard, grader API, or data store. For OpenAI, the legacy Evals platform is scheduled to prohibit writes on October 31, 2026 and shut down on November 30, 2026; avoid introducing a new durable dependency on it. OpenAI publishes a migration example that recreates Evals in Promptfoo; verify behavior and grader calibration after migration because numerical scores need not match. Investigate Datasets and trace grading only after verifying their current lifecycle and whether they meet the required eval contract; do not assume any newer surface reproduces the legacy API.

## Execute a complete evaluation

For a consequential comparison, deliver a versioned plan, actual trial records, scored evidence, a reviewer record, and a decision report. Complete the following sequence on the caller's real task and execution surface.

1. **Predeclare the decision contract.** Record the decision owner, target task population, outcome unit, primary metric, pass threshold, required slices, permitted exclusions, retry budget, stopping rule, and uncertainty method before inspecting decision results. Specify how failed tool calls, partial external state, absent labels and timeouts affect the outcome.
2. **Freeze a valid case population.** Inspect the supplied repository, task schema and fixture examples. Record the holdout revision and case IDs with source and slice labels. Detect overlaps with training or calibration cases using the provided IDs and fingerprints. Quarantine any contaminated case and state which results are ineligible. A repeatedly inspected decision set must be replaced before asserting unbiased improvement.
3. **Execute matched arms on the actual harness.** For a skill evaluation, run each eligible full task with the skill and without it using the same model snapshot, task input, tools, permissions, runtime, retrieval state, limits and scoring contract. Change only the factor under test. Verify at least one success and one failure or recovery case through the real application or caller entry point; an imagined execution trace cannot establish a completed run.
4. **Persist auditable trial evidence.** For every attempt, retain case and arm identifiers, model and prompt revisions, skill version, harness commit, dataset revision, run or session ID, start/end status, tool invocation transcript, observed external state or artifact hash, available usage costs, grader version, and exclusion reason if applicable. Retain retries and failed attempts. Match records on documented identity keys and keep denominators for each arm explicit.
5. **Grade observable behavior first.** Run deterministic tests against the actual output or resulting external state, including malformed inputs and provider or infrastructure failures where those cases are part of the declared population. Use semantic rubrics only where direct checks cannot decide the criterion. Calibrate model judges with independent human labels that include boundary disagreements, and retain each raw judgment and calibration error.
6. **Obtain a genuine blind review when claims require it.** Ask a reviewer who did not implement the candidate to assess anonymized artifacts in randomized order with a frozen rubric and enough reference evidence to decide. Capture the reviewer's distinct session or agent identity, judge model if used, assignment key held outside the review prompt, review timestamp, raw responses, disagreements and the decision rule. A fabricated subagent answer, mocked judge, author self review, or grader unit test does not qualify. If an independent reviewer cannot run, label the claim `unreviewed` and leave the promotion gate open.
7. **Estimate uncertainty and inspect reversals.** Repeat stochastic tasks as prescribed without choosing the best attempt. Compute paired results when pairs are valid, report interval or resampling assumptions, inspect slices, contamination, failures and judge disagreement, and preserve regressions. Distinguish a truly invalid measurement from a product failure under the predeclared boundary; never erase failures from the denominator merely because they make a score worse.
8. **Reproduce the decision.** Run the scorer through its documented caller entry point and test the output schema, result counts, exclusions and negative cases. Report the exact revisions and observed execution level. State which release or skill promotion conditions passed, failed, or remain unknown; do not infer completion from a green grader test or a summary lacking independent review provenance.

## Implementing a scorer against supplied data

When asked to write a scorer or comparison function, **read the caller's fixture README and provided sample inputs before writing code**. The measurement principles above do not define the input API. First make a map of every field in the actual run and task schema, including nesting, identity fields, split labels, status vocabulary, expected output keys, and denominator policy; then write tests directly against that documented shape. A flat `runs[]` stream with `{variant, caseId, outcome}` is different from separate `baseline[]` / `candidate[]` arrays or a nested `{baseline, candidate}` per task. Likewise `resources: {baseline, candidate}` and a `tasks[]` array with `split` labels are different from resources or task sets nested under each variant. Never silently substitute one representation for another.

**Do this afresh for each evaluation contract.** Even two tasks in the same evaluation domain can use `runs[].caseId` in one and `runs[].taskId` in the other. Copy the documented identity key and verify it against the actual supplied task/run objects before defining your TypeScript types or joining records. A successful scorer for one contract is not a schema template for the next. Treat `blindLabels: string[]` as a list of labeled case IDs when so specified; do not require a dictionary keyed by case ID. Record the _type_ of each result too: `contamination: string[]` or `leakage: string[]` is a sorted set of IDs, never its numeric size; `{eligible, passRate}` and `{eligible, passed}` have different meanings. When a fixture exposes no examples, use its stated schema and test both normal and missing/invalid records rather than inventing fallback field names.

- Build separate records for each evaluation arm by joining **the supplied keys** (for example a run's `caseId` or `taskId` to an eligible task ID). Preserve the supplied outcome vocabulary, including an `infra` sentinel where documented. Exclude infrastructure outcomes and contaminated or leaked IDs according to the given contract, while keeping ordinary failed trials in the denominator. Do not invent an extra `status`, `id`, `passed` or `outcome` field to make code compile.
- Count baseline and candidate eligibility **separately** when one arm has infrastructure failure. An infrastructure outcome in one arm does not automatically remove a valid run from the other arm unless the caller explicitly requires matched complete pairs. Preserve the original trace and report the exclusion reason; never treat a missing or invalid run as a pass.
- Keep descriptive per-arm counts separate from paired inference. A caller may require independent denominators without authorizing a superiority claim from their difference. For paired analysis, identify complete comparable pairs separately under the predeclared exclusion policy and report attrition in each arm. Do not rewrite a supplied counting contract to satisfy a different statistical question.
- Distinguish label coverage from release readiness. A coverage predicate can be vacuously true on an empty set under its documented API; that is not evidence of trials, calibrated judgments or sufficient sample size. Validate input separately, test empty populations and missing labels, and withhold the consequential decision when evidence is absent without silently changing the caller's predicate semantics.
- Calculate overlap between training data and the decision holdout from the documented split and fingerprint fields before measuring either arm. Compare resource configurations using the actual representation, and keep leakage, comparability and score gates independent: a resource mismatch can invalidate comparison even when eligible runs can be counted. Blind label coverage must inspect the exact decision holdout ID set after contamination exclusions.
- Verify the full returned object against at least one supplied success case and one exclusion or mismatch case using the real caller entry point. Tests built from a guessed schema can all pass while the production scorer throws on the actual `runs` field or silently reports zero valid trials.
- Before declaring completion, check the exact output shape as well as each count and set: a wrong identity key can silently make every arm eligible count zero, and replacing the required array of leaked IDs with a count can appear plausible while breaking the caller contract. Run the actual supplied fixture tests before reporting a pass.

## Boundaries

- `ml-evaluation` owns evaluation methodology for predictive or statistical ML systems outside generative tasks. Both disciplines inherit shared testing principles and methods for analyzing data; a generative evaluation need not load calibration or classification procedures specific to predictive ML.
- `ai-safety-evaluation` owns dedicated harmful capability, misuse, policy, jailbreak and red team risk evaluation. This skill can supply general experimental rigor without replacing that specialty.
- `agentic-systems` owns agent planning, tools, memory, delegation and authorization. This skill evaluates those behaviors and trajectories but does not design the orchestration architecture.
- `prompt-context-engineering`, `rag-retrieval-systems`, `fine-tuning-training` and `llm-application-engineering` own candidate changes in their respective systems. Keep the decision holdout independent of the optimization loop.
- `verification` proves a particular implementation or artifact meets its contract. `llm-evaluation` owns comparative/representative measurement across variable model behavior.

Use [the maintained source map](references/sources.md) for provider evaluation surfaces. Platform APIs change quickly; the measurement contract above should remain portable when a provider retires an eval product.
