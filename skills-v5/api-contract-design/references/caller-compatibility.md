# Caller compatibility and continuation procedures

Read this when a requested API change combines retries, state transitions, cursor pagination, new enum values, or staged client migration. These are contract examples, not mandatory API shapes or a reason to redesign unrelated endpoints.

## Idempotent mutations and observable lifecycle

1. Read the installed caller behavior first: which key is retried, which body fields define the same logical request, and which response fields are retained. Normalize semantic defaults consistently (for example, omitted `includeHistory` and explicit `false` may mean the same request if the contract says so). Do not conflate distinct account or authorization contexts.
2. Reserve the key against that normalized identity before creating a second side effect. The same key and same semantic request must replay the original operation identifier and the response view promised by the contract, whether that is current state or a stored response. The same key with a different identity must return a stable conflict that is not retryable without creating another operation. Decide key lifetime, race behavior, and scoped ownership instead of relying on a mutable map held inside the process in production. A deliberately local fixture may use process owned state; state its lifetime without adding unrequested infrastructure.
3. Model cancellation by actual lifecycle state. Decide which transitions are legal; repeat cancellation, not found, completed, and concurrent finishing states separately. Preserve existing client access to documented result fields and error codes. Classify retryable versus terminal for the current attempt explicitly and remove queue, cache, database, worker, and other infrastructure topology from public errors.
4. Implement and test through the maintained caller entry point, including a replay, a collision with a changed body, two racing starts when applicable, legal and illegal cancellation states, missing resource, retryable terminal/nonterminal failures, and a view from an installed old client. Confirm the tests **fail** against the original defective behavior, then pass against the repair. A new test file that passes both implementations does not establish regression protection.

## Migrating offset pagination to cursor traversal

Treat an already supplied migration specification for installed clients as the source of truth for implementation and compatibility tests. Read its exact promises before editing; preserve the original reference when it already covers ordering, expiry, behavior of old clients, or telemetry. Record further migration detail in a separate owned artifact when appropriate. A documentation rewrite can obscure whether the installed contract was retained.

1. Preserve the installed `page`/`limit` branch during the agreed coexistence window. Keep its result semantics and the event enum vocabulary used by old clients, attach the contract's deprecation signal, and count real use by old clients. Add a distinct new cursor branch with separate usage telemetry. Do not silently migrate the old request or claim the old branch is compatible because new callers pass.
2. Choose an unambiguous total order such as `(occurredAt DESC, id DESC)` when it matches the data contract. Seek strictly **after** the last returned tuple, preserving the tie breaker and the order direction. Encode or reference that tuple, not a numeric offset that shifts when a newer record is inserted. Build the next cursor from the last item actually returned.
3. Include issuance time and any relevant cursor scope. Apply an authenticated integrity mechanism such as HMAC, authenticated encryption, a digital signature, or opaque server state. A checksum cannot prevent client tampering. Use an existing configured signing seam when available; introducing a new required secret is a deployment contract change. If a signer owned by the process is suitable for the stated scope, document its restart and limitations across instances.
4. Define exactly one token serialization and text encoding, including the alphabet and padding policy. Before interpreting a supplied signed segment, decode and reencode it and require the exact original spelling. Verify authentication, tuple fields, scope, and expiry according to the contract. Alternate padded or noncanonical spellings, including mutations of the final encoded character, must not become another accepted spelling for the same bytes. RFC 4648 explains canonical pad bits; rejecting alternate spellings is this token contract's explicit policy, not a claim that every decoder is required to reject them.
5. Handle newly introduced enum cases for installed strict decoders on their legacy branch only; return the real new value to capable clients. Track expiration boundary and malformed/tampered behavior distinctly if the contract does. An expired valid token and an invalid token can require different public error identities.

**Execute the compatibility matrix:** a newer insert between pages; duplicate ordering values; missing and malformed cursors; a modified signature or final encoded character; exactly at expiry and just after expiry; old `page`/`limit` requests and usage telemetry; new cursor requests and usage telemetry; a legacy strict enum client; and a new client receiving the unmodified enum value. Check both maintained contract examples and executable behavior. Add only scenarios relevant to the requested change, and retain real failures rather than weakening tests or altering fixtures owned by the evaluator.

Do not promise a frozen snapshot merely because keyset traversal survives a newer insert. State what happens to backdated inserts, deletes, and changes to ordering fields when those mutations are in scope. Use the same comparison for sorting and seeking, including string collation for a tie breaker. Check an empty collection, the final page, and restart after an invalid or expired cursor when those outcomes are part of the requested contract.

## Report the boundary of the evidence

State the old and new observable caller promises, maintained artifact and tests, actual regression rejection, runtime entry point exercised, deprecation and limits on key lifetime, and conditions not exercised. A source comment, a diff limited to the schema, a hidden evaluation check, or a mocked clock alone is insufficient proof of runtime compatibility.
