# Prompt Context Engineering

Treat a prompt as a versioned behavioral interface. The deliverable is a working prompt/context construction path, with observable decisions on conflicting instructions, missing evidence, budget pressure, hostile data, and model changes. A prompt that merely looks better does not establish a behavioral improvement.

## Workflow

1. **Inspect the real inference path.** Identify the current provider, model/snapshot, API, role mapping, template/prompt revision, builder code, tokenizer or reported usage, source records, and exact input/output schema. Read the actual implementation and fixture before editing. Verify which parts are instructions supplied through an authoritative transport role and which are merely _text describing_ a role. Resolve version ambiguity against the selected runtime; a previous model's prompting guide is a hypothesis to retest.
2. **Write the behavioral contract before editing.** Specify valid inputs, validation errors, authority order, provenance identity, freshness rules, stable versus task specific material, output type/order, selection or abstention conditions, and recoverability after invalid input. Identify who owns permissions and tool side effects. Translate every consequential claim into a runnable case with an expected result, including failure and recovery; do not infer implementation success from a fluent final explanation.
3. **Keep authority and evidence separate.** Enumerate the _actual_ developer/user instructions, tool results, retrieved passages, summaries, examples for few shot prompting, and interpolated variables. Attach source/version/freshness/trust metadata. Trustworthiness of a tool or document as evidence does not turn it into an instruction. Imperative text, fake role delimiters, XML tags, Markdown headings, and quoted prior turns inside data stay data. Resolve conflicts between instructions of the same authority using the host's ordering policy; report conflicting evidence without allowing it to override instructions.
4. **Make context selection deterministic.** Define an explicit priority for the actual application; preserve input order within a priority. If a current record supersedes a stale record with the same **verified source identity and revision lineage**, exclude the obsolete copy **before** ranking and budgeting, even if the current copy later cannot fit. Do not group records by a generic source label such as `retrieved`, `tool`, or `history`; unrelated records with the same label are not proven duplicates. Apply an explicit age or expiry policy to stale records without a verified replacement rather than silently treating them as current. Compute available input tokens as the applicable request limit minus _only the unaccounted_ output reserve, tool/schema and framing overhead. Validate finite, nonnegative token counts and capacity; a missing limit or a default of zero is not a valid budget. **Reserve the complete cost of every required instruction and evidence item before selecting optional context**, regardless of priority, so optional records cannot consume required capacity. Select complete optional records in stable priority order; when one cannot fit, record its ID and `budget` reason and continue checking smaller eligible records. Record superseded IDs separately, before budget skips, when the output contract needs ordered skip reasons. Do not silently crop a record or quietly discard a required governing instruction. If required context is missing or over budget, return an explicit incomplete/error state under the host contract.
5. **Construct templates without promoting variables.** Put reusable instructions in fixed content that is bound to its role; pass user strings, retrieval text and tool data through typed variables or structured data slots. Validate allowed value types and preserve exact values, including booleans, numbers, null, arrays, unusual keys and strings containing template delimiters or instructions. Escape only at the actual serialization boundary; never parse variable _content_ as prompt structure or use it to construct a privileged role. Distinguish a deliberate normalization rule from accidental coercion. Make the output order deterministic when required.
6. **Choose examples by coverage, not frequency.** Inventory labels and decision boundaries. Explicitly exclude held out examples from the serving prompt; choose a bounded, deterministic representative set per relevant label or behavior so an abundant class cannot suppress rarer cases. Keep examples in a demonstration section with lower trust; preserve a separate immutable evaluation set. Report what was selected and why, and check the token cost against the context budget.
7. **Handle bad or changing context.** Define behavior for missing sources, contradictory current records, stale summaries, hostile retrieved text, mismatched guidance and serving model versions, malformed input, insufficient input budget and violations of the output schema. Surface model/guidance mismatch for revalidation; do not silently reuse guidance written for a prior model. Preserve validation on the application side, along with permissions and authorization checks. A prompt is never a security boundary or an entitlement grant.
8. **Implement and verify the smallest change.** Preserve changes owned by the user and existing API contracts. Run focused tests against the actual builder/consumer, inspect generated output (not only build success), capture baseline and changed behavior at fixed model/settings, and retain regressions. Cover stable ordering, provenance supersession, mixed trust, fit/skip/continue, an absent budget or one with excessive reserves, hostile delimiter values, held out exclusion, imbalanced labels, type fidelity, version change, recovery from bad input and cases adjacent in scope. Never turn a synthetic example check into a claimed model result.

Use [the decision procedure and worked examples](references/operational-protocol.md) when implementing a context selector or a change to the prompt template. Adapt its _policy_ to the application's real schema and provider semantics; the examples are illustrative, not answers to evaluation cases.

## Evidence for completion

Provide a concise, inspectable handoff with (a) the actual model/API/template revision and changed file paths, (b) a provenance/role/trust/freshness map, (c) the exact formula for token capacity, ordering and skip reasons observed in a real execution, (d) representative, negative and recovery test commands with results, and (e) baseline versus candidate outcomes on identical model/settings. Mark missing runs, simulated inputs and unknown provider behavior **unverified**. An implementation, local test pass, deterministic scorer or self review is not an independent blind semantic review; qualification requires real paired full task evidence and an independent reviewer with provenance.

## Boundaries

- `llm-application-engineering` owns provider integration, contracts for structured output and tools, authorization, retries, persistence, latency/cost policy and shipping behavior around the prompt.
- `rag-retrieval-systems` owns corpus lifecycle, chunking, retrieval that respects ACLs, ranking, freshness and selection of grounding sources. This skill owns how context that was already selected is represented, prioritized and trusted inside the prompt.
- `llm-evaluation` owns benchmark construction, grader/judge design, calibration, statistical comparison and contamination controls. This skill requires before/after evidence but does not redefine the evaluation methodology.
- `agentic-systems` owns autonomous planning, delegation, memory, tool sequencing, budgets and completion criteria. This skill may tune the agent's instructions/context without owning the orchestration architecture.
- `ai-safety-evaluation` owns dedicated evaluation of safety and red team exercises. Prompt injection resistance here is a prompt/context trust property and must not be represented as a complete security control.

Use [the maintained source map](references/sources.md) for behavior that is specific to a provider. Refresh rolling provider documentation before encoding assumptions about message roles, context windows, prompting that is specific to a model, or prompt management.
