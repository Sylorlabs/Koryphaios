# RAG Retrieval Systems

Treat retrieval as an evidence pipeline with its own correctness contract. A fluent generated answer does not repair a missed, unauthorized, stale, or wrongly ranked source.

## Workflow

1. **Define the corpus contract.** Identify source systems, authority, tenant/visibility rules, canonical document IDs, revisions, timestamps, deletion/tombstone behavior, supported media/parsers, and the freshness target. Keep source identity stable enough to trace every retrieved chunk back to an exact document revision. When a repository task already supplies an exact input/output contract, schema, or executable checks, implement that bounded contract first instead of expanding the task into a broader RAG redesign. Preserve the supplied data model: do not require or synthesize fields that the contract stores in another record. If ranking signals and authoritative metadata are separate, resolve them through the declared stable identity before applying eligibility or ranking.
2. **Make ingestion reproducible.** Record parser/chunker/embedding/index versions and ingestion status. Preserve structural boundaries and useful metadata, deduplicate revisions, give chunks stable identities, and surface parse/index failures. Do not tune chunk size or overlap from intuition alone; test it against representative information needs.
3. **Enforce authorization before evidence reaches the model.** Carry ACL and tenant metadata through ingestion and apply the user's current authorization at retrieval time or an equivalent protected boundary. Evaluate lifecycle and authorization from the contract's authoritative metadata source, then apply that eligibility before fusion, ranking, or top-k truncation so stale, deleted, revoked, unauthorized, or metadata-missing evidence cannot displace valid evidence. Missing or invalid ACL metadata fails closed unless the product contract explicitly defines another safe policy. Test cases across tenants, with revoked access and missing metadata; post-generation redaction is not an adequate retrieval security model.
4. **Design retrieval stages around the query mix.** Establish lexical, dense/sparse semantic, metadata filtering, query rewriting and hybrid candidate paths as justified by actual queries. Keep candidate generation, fusion and reranking observable separately. Exact identifiers, names and error codes often need lexical support even when semantic retrieval is strong.
5. **Tune ranking against judgments.** Choose candidate counts, fusion weights/windows, score thresholds and reranker settings from a versioned query set with relevance judgments. Track metrics that match the product need, commonly Recall@k for evidence coverage plus Precision@k, MRR or NDCG for rank quality. Inspect query-level regressions rather than only aggregate means.
6. **Preserve grounding lineage.** Pass source/chunk/revision/locator metadata with selected evidence. Citations must map to evidence actually retrieved and used, not merely to a document that exists in the corpus. Keep retrieval provenance available for debugging even if the citation format shown to the user is simplified.
   When a task separates ranking signals from authoritative documents, join candidates to the authoritative record by the supplied stable ID before checking lifecycle/ACL fields, and carry that joined record through selection. Do not add an undocumented fallback field. A function that only retrieves may return locators for its selected results as the caller requires; proving that a generated answer used those results is a separate check at the generation boundary.
7. **Handle missing, stale and deleted evidence explicitly.** Define index-lag expectations, update/reindex behavior, tombstones and cache invalidation. If eligibility filtering leaves no usable evidence, return the contract's bounded no-answer or abstention result rather than filling the gap from model memory. Keep this behavior deterministic and testable for revoked, stale, deleted, unauthorized, and metadata-missing inputs.
8. **Separate retrieval from generation failures.** Persist the retrieved candidate/reranked sets for benchmark queries so a bad answer can be classified as retrieval miss, authorization/filtering fault, ranking/context-selection fault, citation fault, or generation fault. Evaluate answer groundedness separately from search relevance.
9. **Gate changes on corpus-versioned evidence.** Rerun the same query/judgment suite when parser, chunker, embedding, index, query rewrite, filter, fusion, reranker or corpus revision changes. Include ACL leaks, deletions/freshness, queries with no answer, queries with exact keywords and semantic paraphrases, plus latency/cost at the deployed top-k/candidate settings. In repository work, preserve supplied corpus fixtures, relevance judgments, tests, and other user-owned evidence unless the task explicitly asks to change the contract; make the implementation satisfy the evidence rather than rewriting the evidence to fit the implementation.

## Boundaries

For a retrieval change, persist query IDs and corpus/configuration revisions, authoritative eligibility decisions, selected chunk locators, and the command/results for success, denial/no-answer and cases where valid evidence is restored. For system-quality claims, also retain judged per-query rankings, the chosen metric and cutoff, missing judgments, latency and generation/citation checks. A local filter test proves only its exercised boundary; mark unavailable corpus or generation evidence explicitly rather than inventing it or expanding a bounded function's return schema.

- `vector-search-systems` owns vector database/index selection, ANN algorithms, index construction, filtering execution semantics, capacity and low-level search performance. This skill owns the evidence retrieval policy used for grounded generation, from end to end.
- `embedding-systems` owns embedding model selection, dimensionality, normalization, batching, drift and representation-quality evaluation. This skill consumes those representations as one retrieval signal.
- `prompt-context-engineering` owns how already-selected passages are delimited, prioritized and trusted inside the prompt/context window. This skill owns which passages are selected and why.
- `llm-application-engineering` owns the surrounding model/API schema, authorization of actions, retries, fallback and product-level inference contract.
- `llm-evaluation` owns general benchmark/judge methodology; this skill owns retrieval-specific qrels, ranking metrics, citation lineage, ACL/freshness cases and evidence-pipeline regressions.
