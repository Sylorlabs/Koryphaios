# Accessibility Verification

Verify the actual task, not just isolated attributes. Start by identifying the medium, applicable normative/platform guidance, supported input methods, and the user journey being claimed accessible. Automated checks are triage evidence; manual operation and representative assistive technology are required whenever the claim depends on interaction or announced semantics.

## Verification workflow

1. **Define the task and environment.** Record runtime/platform version, app/build, input method, assistive technology and version, text/zoom setting, and the start/end state of the representative task. Preserve supplied environment/version identifiers verbatim; record `simulated`, inferred, stale, or unverified status in separate evidence fields or notes instead of rewriting the identifier itself. Identify which environments are actually available _before_ claiming any live test.
2. **Traverse without the default pointer.** For web/desktop, test keyboard navigation order, reachability, visible and unobscured focus, activation, escape/cancel, and focus restoration. For a modal dialog, enter from the invoking control, test forward and reverse focus containment (including attempts to reach the background), then operate Cancel, Escape, successful Confirm, and rejected Confirm separately. Record the actual return target after each exit. If confirmation removes the invoking control, test and name the logical fallback target instead of claiming focus returned to a removed element. For mobile/device targets, use the platform's representative accessibility service or alternate input model rather than assuming desktop Tab behavior.
3. **Inspect exposed semantics.** Confirm name, role, value/state, relationships, grouping, heading/landmark structure where applicable, validation/error association, dynamic announcements, and whether visible and announced intent agree. Prefer native semantics before adding ARIA or custom metadata.
4. **Exercise state changes.** Verify dialogs, menus, disclosure, async loading, success/error messages, disabled and read only states, validation, cancellation, and recovery. A control being focusable is insufficient if state changes are silent or focus is lost.
5. **Stress presentation without losing operation.** For web, use actual browser zoom (including the required 200% case when applicable), and check the long localized name, reflow, clipping, visible focus and obscuration at the resulting viewport. A narrow viewport or CSS scale is supporting evidence, not proof that browser zoom was tested. For native/mobile, use the actual platform text scaling and orientation settings. Test contrast/color dependencies, target visibility, and system settings for reduced motion and accessibility where relevant to the product.
6. **Capture reproducible observations.** For each required task and state transition, keep an evidence row with the attempted input, expected result, observed result, platform/app/AT versions, capture reference, and whether the observation came from an observed live AT session, instrumented browser/device run, or simulation. Separate the visible result, accessibility tree semantics, and _actually announced_ text; a tree node does not establish what a screen reader spoke. Record failures and blocked steps with the same specificity as passes. Never fill in a missing observation from the fixture's expected answer. Keep the original environment identifiers intact, even if a fixture's `at` or `platform` field is more restrictive than ordinary prose.
7. **Combine evidence honestly.** Run applicable automated scanners and platform inspectors, but reconcile them with manual task results. A scanner pass requires the actual tool/version, invocation, tested app/build/state, run time, and retained report or log; `bun test`, a fixture validator, an accessibility tree dump, or a self-reported zero-finding statement is not a scanner run. If the scanner did not execute, mark it **not run/unavailable**, with no invented `passed: true` or empty finding list. Record false positives, unsupported rules, untested assistive technologies, and residual limitations. A synthetic or simulated task run can verify the synthetic fixture contract, but it cannot support a live browser/device/assistive technology pass verdict. Keep the overall verdict partial or unverified until every required live boundary, announced state, and visible focus check has evidence.

## Evidence and verdict separation

- **For each required check**, report `live observed pass/fail`, `instrumented pass/fail`, `simulated pass/fail`, `blocked`, or `not run`, including the environment, input sequence, observed result, evidence path or timestamp, and reason for gaps. A test named `manual` in a fixture may still be `simulated: true`; the name does not establish live manual coverage.
- **For screen readers**, attach a session observation/transcript of what the specified service actually announced after focus, busy, error, and state transitions. Record whether the capture was heard and transcribed by a tester or recorded by the AT service, with the version and settings. If only DOM/Compose semantics, logs, or synthetic speech are available, report those separately and leave spoken outcomes unverified.
- **For synthetic evaluations**, follow the fixture's required output contract and score its assertions as simulation results. Even if the fixture accepts `manualVerdict: pass`, `androidVerified: true`, or `passed: true` rows, those fields describe fixture success only when `simulated: true` or `liveRuntimeVerified: false`. State the **overall live task verdict** independently as blocked/unverified until the actual required browser, AT, device, and switch-input sessions are observed. Never promote a fixture score or a blind review into native execution evidence.
- **For the final report**, map each falsifiable check to the evidence source, remaining gap, and verdict. Show scanner execution separately; record automation/manual disagreements without averaging them away. A blocked required environment remains blocked regardless of the quality of the simulated output.

## Representative evidence protocol

| Target            | Required observation                                                                                                                                                                                             | Evidence that does not satisfy it                                                                                                   |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Web modal         | Keyboard entry, forward/reverse focus containment, Escape, confirm/cancel, visible and unobscured focus, focus return, accessible title, pending/error announcements, and actual browser zoom with the long name | Source code inspection, a positive scanner score, a Chromium accessibility tree snapshot, or a narrow viewport substituted for zoom |
| Web screen reader | Speech/announcement observations from the specified assistive technology version, tied to each tested state and repeatable input steps                                                                           | `aria-live` existing in markup, synthetic speech strings, or a different assistive technology silently substituted                  |
| Android Compose   | Actual TalkBack spoken name/role/state/navigation, then actual Switch Access scanning and activation, return focus, and maximum text scaling layout                                                              | Compose semantics assertions or generated events without service interaction                                                        |

On Android, run TalkBack and Switch Access as separate input configurations where the platform requires it; document actual accessibility focus movement and spoken switch state under TalkBack, then switch scanning, reachability, and activation using the supported switch-input path. Include the disabled-setting explanation, return from details, and the maximum configured text scaling with long localization. Preserve exact pinned versions and record each configuration independently. If the specified Windows/NVDA, Android/TalkBack/Switch Access, or other required environment is unavailable, report the attainable simulation or instrumentation results with **live verification blocked** and list the missing device, service, input, or capture. An independent reviewer can assess the supplied evidence but cannot manufacture a native observation.

## Boundaries

- `accessibility-practice` provides design/implementation guidance; this skill produces fresh verification evidence.
- `functional-verification` owns correctness of business state. Accessibility verification proves the same outcome remains operable and understandable through alternate interaction and semantics.
- `visual-verification` can establish rendered clipping or focus appearance, but semantic order and assistive technology behavior require this skill.

Use [the maintained source map](references/sources.md) only for the medium it governs; WCAG and ARIA do not automatically define behavior on native platforms.
