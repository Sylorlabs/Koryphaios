# Concurrency Debugging

Identify the **observable contract** before treating timing as the cause: which updates must survive, which state transition may happen once, which work must drain, or which callbacks must cease after teardown? Name each actor, shared object, lock/queue, and the boundary that is supposed to enforce that contract. Distinguish a memory data race from an async **logical race**: an event loop on one thread can lose an update across an `await` with no ThreadSanitizer finding.

Record the source revision, runtime/toolchain, threading or event-loop model, and synchronization guarantees in use. A deterministic schedule remains a concurrency diagnosis when correctness depends on overlapping actors. For diagnosis-only work, report the supported cause and proposed repair; implement and verify a correction when the task includes a fix.

## Establish and replay the failure

- Preserve evidence captured before the fix, ahead of any edits. From existing production traces or a local reproducer, record actor/operation and object IDs, each read snapshot or revision, intended delta, actual committed revision/state, and any resources held or waited on. For a hang, capture stacks plus lock ownership/wait information while it is stuck. Keep observed, simulated, and inferred events explicitly distinct.
- Build a **partial** graph of what must happen before what: program order within an actor, lock release to subsequent acquisition, queue handoff, atomic synchronization under the runtime's memory-order guarantees, task completion/join, and proven callback handoff. A timestamp, log emission order, or two tasks both reaching `await` does not alone prove that one happened before the other. Identify unordered conflicting accesses, a non-atomic read/validate/commit sequence, or the concrete cycle of waits; state what evidence would falsify the hypothesis.
- Use fixture barriers, injected scheduler checkpoints, or a small state machine with two phases to force the _original_ conflicting schedule. For competing writes, pause after both have read and drive **both commit orders**; for lock inversion, pause after opposing first acquisitions and observe each second wait. Record actual results from before the fix for each schedule, including any order that still works. A bounded test watchdog is a diagnostic escape hatch, never the production fix. Avoid sleeps and barriers that themselves introduce a lock cycle.

## Fix the owning boundary

- For a lost update, make the read/validate/commit boundary atomic **per entity**: apply an independent delta to current state, or write only while the expected revision still holds and reread/rebase/retry on conflict. A revision increment alone is no guard, and treating a rejected CAS as success still loses work. Preserve conflict policy within the same field and independence of unrelated entities.
- For deadlock, prove the waiter → resource → holder → waiter cycle and remove its enabling edge with one lock order, shorter lock scope, or explicit ownership transfer. Do not hold a lock while joining/awaiting work that needs it; do not discard queued flushes to make shutdown finish. Timeouts, polling, and removing locks do not establish progress.
- For cancellation, completion, or teardown, define who wins the terminal transition (atomic state/version/epoch check), which effects occur at most once, and when outstanding callbacks are unregistered, drained, or invalidated. An earlier validity check is insufficient if an `await` or reentrant call permits teardown before the effect; protect or revalidate at the effect boundary.

## Check failure and recovery

Exercise a stale/conflicting attempt, cancellation, or failure at the repaired boundary as applicable: no false success or duplicate effect, no leaked ownership, and subsequent valid work on the same entity can proceed. Bound retries and expose exhaustion under the existing conflict policy. For shutdown, account for work accepted before the admission boundary and prove its completion rather than an empty queue alone. A code fix prevents recurrence; it does not restore already lost updates or undo duplicated effects. Report any reconciliation from authoritative history separately from the fix and verify recovery only when actually exercised.

## Verify and report

Turn the schedule from before the fix into an assertion that fails before and passes after the change. Replay **each relevant opposite order**, a nonoverlapping control, and behavior at the ownership boundary (both updates, pending work drained, effects that occur exactly once, or no callback after teardown). Add an explicit, bounded **repeatability regression** when replaying fixed schedules: name the repeat/iteration test, assert the invariant on every iteration, and record the executed count, the schedules covered, and any failures in the evidence report. Repeating the same fixed schedule with two phases is a repeatability check, **not** stress evidence of other interleavings. When extra coverage matters, vary actual actor scheduling, contention, or scheduler seeds within a bounded run; record which schedules occurred, not just the iteration count. Use a supported race detector or lock diagnostic as _additional_ evidence, never as proof of absence. Ensure blocked tests can release all actors on failure.

The repeatability record must be tied to executed assertions, not a plan or a prose count: include a named `repeatabilityRegression` or `stressRegression` object with numeric iterations, the exact schedule IDs/orders, invariant outcomes for each iteration, and failures. A deterministic loop with two phases may establish repeatability; it must not be presented as varied scheduling stress. Candidate tests must also reject the original defect when the harness can replay it, so a control that only passes after the fix or only checks an unopposed path is insufficient.

Report a compact **Concurrency timeline**, **Violated invariant**, actual correction/diff, and **Stress regression** with commands, observed outcomes, and evidence limits. Within Stress regression, distinguish an executed bounded repeatability loop over named deterministic schedules from any genuinely varied scheduling stress. For an evidence JSON artifact, include a clearly named `stressRegression` or `repeatabilityRegression` object with numeric `iterations`, the tested orders, and observed outcomes; calling a test "bounded replay" without this record can hide whether it actually executed repeated assertions. If original execution or a detector was unavailable, say so rather than inventing a passing observation.
