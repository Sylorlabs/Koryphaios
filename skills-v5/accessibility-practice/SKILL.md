# Accessibility practice

Own the design and implementation requirements for equitable access. When the request is to _test an implemented experience_ or certify a result, use `accessibility-verification` for the observed verdict; do not turn a requirements review into a reported session with a screen reader. A usability study of general learnability belongs to `usability-evaluation` unless disability access is an explicit task outcome. Accessibility can also be a facet of an editor, game, native interface, or physical control design: keep the primary medium's specialist involved.

## Time-bounded workspace delivery

When a task has a hard execution deadline, budget for **writing and checking the actual artifact**, not just reasoning about it. Use the known wall clock limit; if none is provided, use the same order of writing early without inventing one. Checkpoints below are approximate fractions of the available time (for a budget of 180 seconds: about 18, 54, 108, 144 and 162 seconds elapsed); adjust to the scope, but reserve the final 10 to 15% for validation and completion.

1. **By ~10%: discover the contract.** Read the workspace README, its referenced scope corpus and output instructions once. Extract the **exact output path, schema, required task IDs and required information-channel IDs**. A corpus may contain multiple media: use the subset the README assigns to this deliverable, not every unrelated identifier. Check whether a real app, device or assistive technology runtime exists; do not infer that a synthetic fixture is executable.
2. **By ~30%: persist an initial parseable file.** Create the requested file at its exact path with the required top-level arrays and one distinct entry per scoped task/channel ID. Start with concise, task specific goal, barrier, alternative and recovery content; include at least one verification row per task with a concrete expected result/method and truthful execution status. Use short incremental writes and parse after saving. This is an **in progress checkpoint**, not permission to submit empty fields, repeated boilerplate or unfinished records.
3. **By ~60%: establish functional depth.** Complete every required field and equivalent task path, including the alternative's action, perceivable decision information, consequential failure, recovery invariant and owner. Fill all channel alternatives and the negative state regression oracles. Prioritize the task's severe failures and medium specific behavior before optional elaboration; follow the editor/game cases below where applicable. Update the file on disk instead of composing a long unsaved response.
4. **By ~80%: complete verification coverage.** Include the required distinct platform, assistive technology/feature, alternative input, critical-state and recovery combinations. Each row needs a reproducible method, expected observation, execution status, risk and provenance fields. A missing live runtime means **planned/untested** with `observedResult` and `evidenceRef` set to `null`, never invented speech, controller behavior or a measured pass. Treat a genuinely attempted and blocked run separately.
5. **By ~90%: verify and finish.** Parse the saved artifact, compare actual ID sets (including duplicates and omissions) with the selected scope, verify required fields and that each task has a matrix row, check platform/input/negative-path coverage and evidence-state consistency, and correct gaps. Report the saved path and only checks actually run before the deadline. Stop optional browsing, speculative architecture, repeated scope reads and prose expansion once the contract passes these checks.

**Keep bounded designs concise enough to finish.** For a game with six tasks and five channels, or a similarly sized task, aim for roughly 16 to 24 KB of meaningful JSON, adjusting only when actual requirements need more. Give each task a specific alternative and recovery, each channel an independently usable delivery behavior, each critical state an executable verification plan, and each oracle a measurable negative path. Prefer a compact structured field to repeated prose, a single thorough row per task plus any essential distinct state over speculative matrix permutations, and a short system overview over duplicated task contracts. Never compress away the requested IDs, equivalent outcome, failure/recovery behavior, ownership, provenance or verification status. **Once the file passes parsing, IDs and checks on required fields, finish the response immediately**; additional commentary and embellishment can consume a hard task budget and invalidate a complete saved artifact.

If time is tight, compress wording and optional explanation **before** reducing required task/channel coverage, concrete alternatives, recovery or verification. An early file is a recovery checkpoint; a final file must be substantive. Never solve a deadline by treating proposed checks as observed device output or by asserting unverified accessibility conformance.

Start with the actual medium, platform/toolkit, applicable standards or policy, and the critical tasks and consequential states people must complete. Capture the entry point, successful end state, failure/cancel/recovery path, users' control over time, and the environment. Consider sensory, motor, cognitive, speech/language, temporary, and situational constraints together rather than designing for a single assumed persona. WCAG 2.2 applies to web content; Apple/Android platform guidance, game accessibility guidance, or the product's safety obligations may govern other surfaces. Do not assume browser mechanics apply to every medium. Do not transplant DOM, ARIA, CSS, browser zoom, or Tab order into native, terminal, game/spatial, embedded, API, or physical control interfaces.

Build a _task, barrier, and alternative_ contract. For every essential action or status, record the barrier, a feasible alternate input or output channel, how that route reaches the same important result, and the fallback when the preferred channel or device is unavailable. Do not make critical meaning or operation depend on one sense, color, spatial position, sound, fine motor gesture, memory burden, strict timing, or motion alone when a practical equivalent is required. Prefer native semantics, controls, focus/selection behavior, scaling, narration/screen reader APIs, alternative input paths, captions/descriptions, and system accessibility preferences before recreating them with custom behavior.

For a bounded workspace task that requests a JSON contract, deliver the complete requested file before explanatory prose. Read its README and source scope first, and preserve every supplied exact task and information channel identifier. Where the schema calls for task contracts, create **one structured record per task** with `taskId`, concrete successful `goal`, `barrier`, independently usable `alternative`, consequential `failureState`, `recoveryInvariant`, and `owner`. Where it calls for channel alternatives, cover each named channel with the information it conveys, its redundant alternative, and delivery behavior; a keyword inventory or one generic catchall row is insufficient. Add concrete regression oracles with reproducible triggers, the broken behavior to detect, and the invariant proving recovery, especially when content is recycled, delayed, interrupted, or input devices disconnect.

Treat supplied IDs as join keys, not examples to paraphrase. Check that every task has a distinct, complete contract **and** an associated verification row; every required information channel has its own alternative; and every consequential failure has a testable recovery invariant. A proposed alternate route must name the input action, the perceivable information available at decision time, the resulting state, and how to recover after failure. Merely listing “keyboard,” “captions,” “screen reader,” or “controller remapping” does not establish an equivalent way to finish the task. Write the requested artifact to disk, parse it, then compare the exact task/channel IDs and counts to the supplied scope; a prose-only answer is not a completed file task.

For custom trees, grids, virtualized lists, live diagnostics, and dialogs, specify the exposed name, role, state, relationships, logical navigation/reading order, focus versus selection, action alternatives, and announcement timing. **Anchor focus and selection to logical item identities, never recycled visual rows.** If an item persists through virtualization, preserve or restore its identity and context. If filtering removes it, choose an intentional surviving target (or the filter), expose why focus/selection changed, and provide a way to navigate back. Do not steal focus from someone typing into a filter or editing a document. Differentiate keyboard/assistive technology focus, selection, caret, and scroll position; a labelled control that cannot complete the underlying task is still a failure. Determine the actual toolkit before prescribing APIs: WAI-ARIA tree/grid patterns are for web controls; native Windows UI Automation or macOS accessibility APIs have different contracts.

For asynchronous diagnostics, expose severity, affected location, actionable content, and a navigable review path without moving the editor caret. Prioritize consequential notifications; coalesce repetitive updates and offer details on request so announcements do not drown out work. For a conflict dialog, preserve access to local/remote changes, a cancel/undo path, and a meaningful focus/caret return. Model unsaved edits, **locally durable** edits, sync pending, sync failed, and remotely confirmed edits as separate states; never report a remote save before confirmation. Specify how an interrupted save preserves/restores the user's latest local work and version identity. Include pending, failed, cancelled, stale, restored, scaling, contrast and motion states, with observable failure and recovery behavior.

For games and other interactive media outside the browser, map each critical gameplay or navigation task to suitable input, perception, communication, and recovery alternatives for that medium. Treat remapping as a recoverable transaction: reject or resolve Confirm/Back/Pause collisions _before_ saving, keep menu escape/reset usable with a feasible alternative input, and update control hints after bindings change. On disconnect, describe how the player discovers lost input, reconnects, and regains a known gameplay/menu state; offline pause may be possible, while online cooperative play continues in shared time. Do not promise a global online pause. Account for player safety, difficulty and competitive integrity when proposing timing or assistance changes.

Give dialogue, meaningful audio other than speech, directional threats, brief combat telegraphs beyond color, rapid status changes, and cooperative instructions independently usable channels. An alarm alternative must convey source/direction, urgency and actionable timing, not just “sound occurred.” Narration of frequent HUD changes needs priority and throttling plus a way to query exact status; it must not mask urgent threats. Specify caption/narration customization, motion/camera controls, scaled HUD and dense upgrade-tree navigation with stable logical selection, purchase confirmation and recovery. Provide cooperative actions that do not require voice and remain usable during gameplay. Do not reduce game behavior to a generic web checklist.

Produce requirements that can be implemented and checked: identify the responsible surface/component, behavior on each supported platform, accessible interaction invariant, relevant state transition, acceptance check, and priority based on task consequence. Define a verification matrix before claiming success. Bind each representative critical task/state to platform/device and version, input method, assistive technology or accessibility feature and version, expected behavior, evidence method, execution status, observed result, and artifact reference. Use **planned**, **passed**, **failed**, **blocked**, and **untested** distinctly; a design proposal row is planned, never passed. Separate automated/static checks from manual assistive technology, alternative input, visual, auditory, cognitive, and recovery checks when those categories apply. A synthetic trace or accessibility tree is useful evidence about its own surface, but cannot establish spoken announcements or actual device task completion. Record defects, unknowns, untested combinations, and residual risk, especially with virtualization, scaling, motion, interruption, or platform accessibility APIs. Route execution and conformance evidence to `accessibility-verification`; missing hardware or assistive technology keeps its row unverified.

For each named task in a structured verification matrix, include the intended `platform`, assistive technology or feature and `input` configuration where relevant, `expectedObservation`, reproducible `method`, `status`, `observedResult`, `evidenceRef`, and residual `risk`. Specify the triggered negative/recovery state, not only the happy path. If toolkit/build/device/AT versions are unknown, explicitly mark them **to establish at execution**; never invent a measured environment to make a planned row look concrete. If the required runtime is absent, use `planned` or `untested` and keep `observedResult` and `evidenceRef` null. Distinct representative platforms and alternate-input paths need separate rows as appropriate; a general prose mention is not test coverage. Parse the saved output, count task/channel/matrix records against the supplied scope, and confirm protected evidence was not modified.

Use `blocked` only for an execution attempt that actually encountered a specific unavailable device, permission, dependency or runtime, and record the attempted environment and blocker in the risk/notes without inventing an observation. `planned` means a proposed check; `untested` means the combination was identified but not exercised. Only an observed execution can support `passed` or `failed`, with the actual outcome and retrievable evidence. Keep example announcement strings in `expectedObservation`; neither anticipated screen reader speech, a synthetic accessibility tree, nor a scorer passing a structured design artifact belongs in `observedResult` as an actual assistive technology session. A blocked or unexecuted row is never evidence of product conformance.
