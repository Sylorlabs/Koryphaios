# Visual interface design

Treat visual direction as a constrained system tied to real product evidence. When the task supplies screenshots, token files, state inventories, structured artifact schemas, sample content, or existing components, inspect those first. Preserve approved product facts, information architecture, interaction behavior, field names, and existing identity tokens unless the brief explicitly authorizes a change. Distinguish assets actually present from screenshots, examples, or checks mentioned in the brief but not supplied; never imply a missing input was inspected. A scenario's `fixture://` handle and list of required inputs are pointers to evidence, not evidence that those inputs were received. Read accessible fixture sources and scenario specifications; record missing or inaccessible materials and keep their dependent checks unverified.

## Workflow

1. **Ground the brief.** Establish the product or page kind, audience, real content, task priority, medium, target platforms and themes, existing assets and tokens, supplied state inventory, density, viewing conditions, accessibility constraints, and motion capability. Read the actual supplied files and output templates, including any README or evidence packet. Trace each preserved source fact or token to its output field and each design change to the source constraint that justifies it; mark unavailable inputs explicitly. For a bounded repository artifact, satisfy its exact schema and output contract before broader exploration.
2. **State the visual direction.** Explain what is primary, secondary, grouped, quiet, urgent, interactive, or stateful. For cross platform work, identify which decisions express shared product identity and which adapt to platform conventions instead of making every surface identical.
3. **Encode a reusable system without breaking the output contract.** Make typography, spacing, alignment, grouping, contrast, color, imagery, iconography, borders or elevation, radius, density, and motion reinforce the same hierarchy. Inspect the schema or existing JSON before writing: keep each required field at its specified location **and type** (number versus object, array versus named map, string versus nested object), preserve supplied token values and enum/identifier spellings exactly, and keep optional detail in additional fields. A visually richer artifact that changes the required data shape is incomplete. Specify reusable icon size, stroke or weight, baseline alignment, state meanings, and justified platform adaptations. For motion, name the transition or state change, why it communicates information, its timing, and an equivalent static or reduced motion presentation.
4. **Design the approved interactive states.** Inventory the supplied controls and their existing triggers before styling them. Specify the visual response for hover where supported, visible focus, pressed, selected, disabled, busy, validation/error, and recovery where applicable. Make actionable controls recognizable without relying on hover, and keep essential status visible after pointer or keyboard focus moves. State how target size, icon/text alignment, content overflow, and hierarchy behave at supported density and text scales. Do not add controls, transitions, or recovery behavior absent from the approved interaction contract.
5. **Make dense states measurable.** Define density and hierarchy ready for implementation with concrete dimensions or token values where the artifact calls for them. Distinguish primary actions from secondary treatment, cover every supplied state, and keep table, detail, filter, navigation, canvas, or other named surfaces traceable to the brief. Specify semantic status with text and/or icon as well as restrained color, including which severities receive emphasis. Do not add sticky behavior, action choices, retry/confirmation flows, density preferences, or new product states unless the supplied contract already supports them.
6. **Use redundant state signals.** Color may reinforce status or severity, but labels, icons, shape, borders, text, or other cues without color must preserve meaning. Define visible focus, behavior with large text and localization, and the informational purpose plus a reduced motion fallback for any motion introduced.
7. **Verify representative states.** Build a matrix from the actual supplied surfaces, states, themes, platforms, widths or scales, and content extremes. Include sparse and dense content, long or localized text, loading or progress, empty, error, disabled, selection and focus where relevant. For each row record the input or fixture, platform/theme/viewport/text scale, interaction trigger if any, expected visible condition, method, **observed result or planned/unverified status**, and evidence location. When a running UI or faithful interactive prototype is requested, exercise existing controls and inspect the resulting states with pointer and keyboard where supported; check focus, selection, feedback, scrolling, clipping, and return to normal. If evidence from rendered output or a faithful prototype is required, create a representative UI artifact, render it in the available medium, inspect the result, and cite the capture or reproducible check; a prose checklist, unrendered HTML, static mock with dead controls, or uninspected prototype does not prove the visual result. Browser emulation is not evidence of native macOS or Windows behavior. If the supplied evidence includes measured geometry or capture sidecars, quote the field you relied on (for example the element whose recorded width exceeds the frame) rather than describing an impression, and list clipped and truncated elements by the ids that evidence uses. If rendering is unavailable, describe the limit and leave those checks unverified.
8. **Run a critique against generic defaults.** Treat gradients, glass panels, card grids, serif heroes, monospace labels, extreme asymmetry, shadows, and similar defaults of generated design as prompts for justification rather than automatic choices. Remove treatments that do not serve the supplied content and identity. Never invent testimonials, users, metrics, activity, controls, or domain facts.
9. **Close on evidence and compromises.** Reopen or parse final artifacts, confirm preserved tokens and source evidence remain intact, check that the representative matrix names the actual contract conditions, and report only verification that was actually performed. Keep an explicit register of unresolved visual, platform, density, accessibility, and motion tradeoffs with the competing constraints, affected state, proposed decision, and next check in the real world or owner. For example, shared density tokens versus native font/control metrics requires checking both platform renders, not assuming identical pixels. A claim of no open compromises needs observed evidence, not a missing section. Leave unavailable rendering, platform, or accessibility evidence unresolved.

Maintain a compact source ledger beside the direction: source path or packet identifier, fact or token preserved, output field or decision that uses it, and `observed`, `provided`, `blocked`, or `unverified` status. A fixture URI, scenario requirement, or generic domain description is not a supplied screenshot, asset, content sample, or token value. Do not fill missing source rows with plausible product facts.

Keep visual ownership explicit. Do not add confirmations, retries, sticky behavior, density modes, loading behavior, navigation, or action choices unless the supplied interaction and state inventory already contains them. If a visual proposal depends on one of those behaviors, record it as a dependency or open question rather than silently changing the product contract. For each motion token, name the state transition and informational purpose; for each icon rule, specify size, weight or stroke, baseline alignment, and the meaning it carries without color.

## Deliver artifacts first when editing a workspace

- For a full task scenario, map each declared falsifiable check and required artifact to a concrete output and a verification row before implementation. Distinguish the scenario's promised screenshots, tokens, and content from assets actually available to inspect; a synthetic fixture description is not a substitute for source content. Preserve every check even when an input or rendering platform is unavailable.
- If the task requests an interactive screen or prototype, make the smallest complete runnable surface using approved fixture states and existing behavior. Open it and exercise each representative state before claiming the controls work; a static visual system JSON or screenshot alone does not complete an interactive deliverable. Record the launch/inspection method and observed result in the evidence matrix.

- Inspect the supplied source packet, requested output paths, existing templates, and required field types before drafting prose. Produce the smallest **complete valid artifact set early** within the available execution budget, then refine visual quality. A detailed direction with missing or unparseable required files is an unfinished task.
- When the requested deliverable is a visual system in machine readable form, treat it as the primary result. Replace every empty placeholder in the supplied artifact before writing a design rationale. In a JSON system, keep the source field names and types: preserve `tokens` and exact identity values, enumerate each requested `theme`, `platformAdaptations` entry, and `state`, and give every required platform a concrete adaptation rather than an empty object. Use numbers for measurable density (`compactRow` and `comfortableRow`, with the compact value smaller), and put semantic aliases in separate optional fields. Do not move required fields under a newly invented wrapper.
- **Keep the machine readable contract paths and source values stable.** An empty starter object does not authorize arbitrary nesting. Prefer the direct primitive fields and string identifier arrays suggested by the starter when no more precise output schema exists. If an actual consumer explicitly supports equivalent named theme/state maps or structured token aliases, use those accepted forms and independently check that every required identifier and original brand value survives (for example, `radius.control` and `typography.scale`). Do not introduce invented wrappers such as `tokens.brand` unless the consumer supports them. Preserve the complete supplied typography scale as well as accent, spacing, and radius; omitting a less prominent brand token still breaks the design contract.
- **Keep enumerated signal maps free of metadata.** When the source enumerates severities and the starter provides `severityEncoding: {}` without a nested value schema, use exactly those severity identifiers as keys, with a concise string per severity defining its visible label plus icon, shape, or border cue and any permitted color reinforcement. Put global limits, lists of color emphasis, and structured display recipes in separate fields; they are not extra severity entries. Follow an explicit schema if it specifies structured values.
- Encode focus, color independence, text scaling, and localization as **checkable data** when the contract has accessibility fields: `focusVisible` and `colorNotSoleSignal` should be booleans, `minTextScale` should meet the supplied scale, and `longLabelStrategy` should explain how lengthy localized names remain usable. If the source declares a primary action, use its exact identifier in `hierarchy.primaryAction` and explain how secondary controls are quieter. If it declares severity names, encode all of them with text or icons and reserve color for only the permitted subset. If the brief criticizes card/shadow excess, explicitly bound `shadowLevels` and `cardNesting` as numbers.
- Before editing, enumerate the required keys and value types from each existing output template, the exact immutable values and identifiers from the evidence packet, and the minimum verification conditions from the brief. Complete those fields in the first saved version. For example, a numeric spacing scale must remain a numeric array even when adding semantic spacing aliases, a value for row height must be numeric, and a required state list must remain an array containing every supplied state. Design descriptions do not substitute for these fields in machine readable form.
- Write the verification matrix in the requested output file alongside the first valid artifact. Use a Markdown table with condition, expected result, method, and observed/planned/unverified status, plus evidence/source locations when available. Include **every supplied surface and state**, then the real cross product of representative platforms, themes, density, width, large text, long localized labels, focus, and primary/status conditions applicable to the brief. Name the provided minimum width, factor for text scale, and label length explicitly. A paragraph listing the conditions, or a table that omits a supplied surface such as filters or timeline, is incomplete. Record actual observations separately from planned checks; a TODO or a render the author attests to without a usable capture or reproduction procedure cannot close verification.
- Prefer one complete write per output file, or one patch operation targeting that path per patch call. Do not bundle multiple patch operations for the same path: some patch tools reject the entire patch. Apply later corrections in a separate operation after verifying the first write.
- If a patch is rejected, inspect the current file before retrying. Replace only the incomplete output artifact with one complete valid write, then parse it and check against the source packet; do not repeatedly issue the same invalid patch with multiple operations or spend the remaining budget on prose while a required artifact is missing.
- Immediately parse each generated JSON file, verify required keys/types and exact preserved identifiers, and confirm the requested files exist. Check that any protected evidence packets were not changed. Recheck after visual refinements.
- **Reconcile the artifact with its consumer.** Independently read back the final files and compare direct key paths, array element types, exact brand primitives, identifier membership, and maps with the source packet and any declared output schema. A verification script you wrote yourself proves only its own assertions; do not claim contract compliance solely because it passes. If another checker reports failure, compare the actual stored shape and coverage before accepting either interpretation. In the verification matrix, name the supplied stress condition plainly (for example, a "long label" case with its real character count, minimum width, theme, and platform) so each check is traceable without inference.
- When the evaluation harness owns paired experiments or blind judging, leave those reports to the harness. Deliver the visual work and its independently checkable evidence without inventing pair results, successful rendering, or reviewer approval.

This skill owns visual direction and rendered state critique. Route behavior to `interaction-design`, organization to `information-architecture`, wording to `content-error-design`, and formal accessibility conformance to accessibility specialists.
