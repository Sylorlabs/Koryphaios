# Query plans that vary by parameter

Use this when the slow tail depends on tenant, status, timestamp range, or other skewed bind values. The goal is to explain the selected plan for **each important parameter class**, then choose the smallest intervention that lowers the affected tail without worsening the workload.

| Observation | Next discrimination | Conditional choice |
| --- | --- | --- |
| Enterprise p99 is high while small tenants and the median look healthy | Compare actual plans and row/buffer counts for small and large tenants **with the application's prepared statement mode** | Target the bad parameter class and plan choice; do not use the global median as success evidence. |
| Actual rows differ greatly from estimates | Check statistics freshness, column correlation, representation of the most common values, and custom/generic execution | Test `ANALYZE` or multicolumn statistics where they affect the misestimate, then remeasure actual plans. |
| Prepared statement uses a generic plan across highly different tenants | Use `EXPLAIN EXECUTE` with representative binds; in PostgreSQL, `$1` in a displayed plan indicates generic while substituted values indicate custom | Determine whether refreshed statistics make the automatic choice adequate. If not, test **scoped** custom planning and its planning CPU cost; avoid forcing all app connections. |
| Proposed index duplicates an existing leading key | Compare existing key order, sort coverage, index size, predicate shape, and candidate plans | Reject if the new index is not used or does not improve the target; a shorter index is not automatically useless, but must justify maintenance and storage. |
| Plan operator is reasonable but total request time varies | Compare lock waits, connection pool queue, I/O, heap fetches, spills, and cache | Fix the observed wait/resource bottleneck before creating more indexes. |

For PostgreSQL 17, a **generic** plan cannot use a particular supplied tenant value for selectivity. `CREATE STATISTICS ... (mcv, dependencies)` plus `ANALYZE` can improve estimates for correlated equality predicates when the planner has useful values, but creating the statistics object alone collects nothing. Statistics may change the choice of generic versus custom plans after replanning; prove the observed change rather than asserting statistics alone make a generic plan tenant aware. Check `pg_prepared_statements` if accessible, and distinguish the application's real prepared path from isolated literal SQL. Treat an engine described merely as compatible with PostgreSQL as unverified for plan settings specific to PostgreSQL.

When plans can be executed safely, capture estimated/actual rows, loops, execution time, buffers, sort/spill, and relevant waits. Compare correctness of the same query and representative p50/p95/p99 for both common and pathological binds. For each candidate record the target p99, planning overhead, write throughput/CPU, lock impact, storage delta, and the p99 of neighboring queries. Include a negative path (another bind class or a competing write workload) and a rollback/retest plan; choose a statistics change over an added index or global setting only if **the measurements** favor it.

Sources: [PostgreSQL 17 PREPARE](https://www.postgresql.org/docs/17/sql-prepare.html), [EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html), [planner statistics](https://www.postgresql.org/docs/17/planner-stats.html).
