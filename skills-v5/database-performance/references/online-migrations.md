# Bounded online migrations and backfills

Use this when a schema change or a backfill of a derived column is safe on staging but delays production writes. Determine the **actual engine/version**, row count, the ratio of staging to production, peak write rate, long transaction distribution, constraints/indexes, and the exact SQL. Identify which operation waits for a strong lock, rewrites the heap, scans the table, or holds row locks. In PostgreSQL, even an `ALTER TABLE` that only changes metadata normally needs a brief `ACCESS EXCLUSIVE` lock and can queue behind an old transaction, blocking later writers.

For a large PostgreSQL table, the following is a **conditional shape**, not a transaction containing every phase:

| Phase                | Decision and gate                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prepare writers      | Decide how new/changed rows get the correct derived value before the backfill (application dual write or verified database mechanism). Specify how invalid source values are handled; do not quietly insert nulls or weaken isolation.                                                                                                                                                                                                                                                    |
| Add column           | If supported by the actual version, add the nullable column **with no default that rewrites the table** in a short, separately committed DDL transaction. Bound lock acquisition; abandon the attempt when it queues behind long transactions.                                                                                                                                                                                                                                            |
| Backfill             | Use ranges of the primary key and small committed batches, selected from measured batch time and writer impact. Compute from current row values, update idempotently, and persist the cursor **after** each successful commit. Reconcile rows changed or inserted behind the cursor and any skipped locked rows before asserting completion.                                                                                                                                              |
| Optional index       | Add only if plan evidence demands one. PostgreSQL `CREATE INDEX CONCURRENTLY` allows writes but takes longer and must execute **outside** a transaction block; inspect invalid indexes left after a failed attempt and deliberately clean up/rebuild before retry.                                                                                                                                                                                                                        |
| Enforce NOT NULL     | Once writers and backfill cover every row, add a `CHECK (derived_col IS NOT NULL) NOT VALID`, then `VALIDATE CONSTRAINT` under representative writes. PostgreSQL 17 validation uses `SHARE UPDATE EXCLUSIVE`, which normally permits ordinary writes. Only after validation, perform `ALTER COLUMN derived_col SET NOT NULL` in a bounded lock window; a valid proving `CHECK` lets PostgreSQL 17 skip the full validation scan, but `SET NOT NULL` still requires its brief strong lock. |
| Confirm and clean up | Verify null count, correctness of derived values under concurrent updates, constraint/index validity, writer latency, throughput, and changed query plans. Retire temporary compatibility behavior only when both data and deployed writers are safe.                                                                                                                                                                                                                                     |

Use both `lock_timeout` and `statement_timeout` where the engine supports them. Choose values from the write SLO and measured phase durations (for example a lock acquisition budget of 2 seconds); a statement timeout must accommodate the bounded work it governs. Avoid holding transactions open over many batches, and do not blindly retry a DDL call after a timeout. Inspect blockers and lock queues, cancel the current phase, then reschedule a bounded attempt. Keep prior committed backfill work; on interruption resume from a durable checkpoint and perform a final sweep for missing or incorrect rows. Validate the abort case during an interruption in the middle of a batch or backfill and show zero duplicates/skips or precisely explain any unresolved ones.

For PostgreSQL, a `DEFAULT` expression cannot refer to another column in its row. Verify the proposed SQL's legality instead of treating `DEFAULT derive(payload)` as an executable way to derive a new field. Use application/trigger maintenance or an explicitly evaluated alternative. Lock/write availability and correctness are both release gates: a fast scan that creates a writer queue is a failed migration. Compare plans after the migration and p95/p99 of neighboring queries under realistic concurrency at production scale, and include an abort/recovery record with observed waits and remaining cleanup.

Sources: [PostgreSQL 17 ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html), [CREATE INDEX](https://www.postgresql.org/docs/17/sql-createindex.html), [CREATE TABLE default expression contract](https://www.postgresql.org/docs/17/sql-createtable.html).
