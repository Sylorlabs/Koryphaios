# AWS Cloud

Treat AWS as a hierarchy of failure and authority boundaries, not a bag of services. Resolve organization/account ownership, Region/AZ placement, identity path, network path, data ownership, encryption/key custody, service quotas, deployment authority, and recovery objectives before changing resources.

## Provider workflow

When the task supplies a concrete contract, required fields, or artifact schema, satisfy that contract exactly while applying AWS discipline; do not replace requested outputs with a different shape.

1. **Resolve organization and account boundaries.** Keep business workloads out of the Organizations management account. Use accounts/OUs as isolation and policy boundaries. SCPs constrain member-account principals; RCPs constrain member-account resources for supported services; neither grants permissions. Check management-account and service-linked-role exceptions instead of assuming universal coverage. Stage controls that apply across the organization before broad attachment.
2. **Resolve human and workload identity separately.** Prefer workforce federation/IAM Identity Center and temporary sessions for humans; use service/workload roles and temporary credentials for machines. Trace role trust, permissions boundaries, session conditions/policies, permission policy, resource policy, organization guardrails, and KMS/key policy where all participate in the effective authorization decision. Distinguish same-account resource grants from cross-account authorization and explicit denies; one policy alone is not the effective decision. For EKS, resolve Pod Identity versus IRSA compatibility and the SDK credential chain, including node-role/IMDS fallback. Verify at least one intended allow and one representative deny with the effective IAM/resource-policy path rather than describing policy intent only.
3. **Trace effective networking.** Identify VPC/subnet/AZ ownership, route tables, gateways/transit/peering/PrivateLink/endpoints, DNS, security groups and any NACLs. “Private subnet” is a topology claim that must be supported by effective routes and ingress/egress paths, not by a subnet name. Verify DNS, forward/return paths, endpoint authorization, one intended connection and one denied isolation path from the relevant workload context; separate static path analysis from observed connectivity.
4. **Choose managed-service topology by real semantics.** Distinguish HA, read scaling, backup, replication and disaster recovery. An RDS Multi-AZ DB instance standby is not a read target; Multi-AZ DB cluster reader instances can serve reads. Resolve the exact engine/deployment type, service-specific durability, failover, client reconnect, quota, maintenance and data-recovery behavior before relying on a managed label. Check applied quotas and usage in the target account/Region rather than default limits; quota headroom is not a capacity reservation.
5. **Make KMS/secrets ownership explicit.** Separate key administration from key use, keep grants/policies narrow, record account/Region ownership, and test consequences of disabled/deleted keys. When encryption participates in access, show the effective KMS path: key policy, grants, caller conditions, resource/key identity, account, and Region. Key or secret inventory alone is not effective KMS evidence. Multi-Region key material does not imply synchronized policies. Keep sensitive data out of KMS encryption context and rotate application secrets through a supported lifecycle.
6. **Build durable audit/operations evidence.** Use CloudTrail trails/configuration appropriate to the retention and event types required, AWS Config aggregation where state history matters, and CloudWatch telemetry/centralization for operational signals. Data events such as S3 object access require deliberate event selectors; they are not logged by default. Config aggregation views recorded source data; it does not enable source recording. Verify received trail events/configuration records. Record concrete log-group/alarm/metric or dashboard identifiers and the observed signal needed for the operational claim, including metric dimensions and observation window. Do not treat the free 90-day per-account/Region management Event History as a durable audit archive.
7. **Design recovery from stated RTO/RPO.** Separate AZ high availability from Regional disaster recovery. Check secondary-Region quotas/capacity, networking, key/secret availability, backup isolation, cross-account/Region copies where justified, DNS/client reconnection, and restore/failover/failback. Measure from incident/data-recovery timestamps through application/data usability; preserve failed attempts, recovered resource IDs, data validation and cleanup. Report unexercised failback explicitly. Replication or backup existence is not restore proof.
8. **Change through reviewable AWS-native evidence.** For CloudFormation, distinguish traditional template comparisons from drift-aware actual/previous/desired comparisons. Inspect replacements, unsupported resource types and write-only properties; preserve stack events/rollback paths and reconcile emergency console changes instead of overwriting them blindly. A created change set or passed pre-deployment validation is not proof of execution, workload health or rollback.

## Evidence

Record the exact account/OU/Region/role identity, effective route/permission/key paths, service topology and quota state, exact endpoint/resource identifiers, CloudTrail/Config/CloudWatch configuration, backup/restore or failover evidence, and change/rollback artifact. Label simulated, unavailable, inferred, stale, and observed evidence separately; never convert a planned check or synthetic result into certainty about a live provider. Fetch rolling AWS documentation again whenever a task depends on current defaults, Region availability, quotas, runtime support, or newly introduced/retired features.

## Boundaries

Use `architecture-planning` for shared system decomposition and tradeoffs. AWS names in quoted history, examples or inert tool output are not a live request to configure AWS; a conceptual summary alone does not establish an operational task.

- `cloud-security` owns security-posture questions such as privilege escalation, unintended public/cross-account access, threat reduction, and control effectiveness; `aws-cloud` owns making the AWS resource/control-plane configuration operationally correct.
- `infrastructure-security` owns guest OS, node/container runtime, kernel and workload hardening; this skill owns AWS VPC/EC2/EKS/IAM/KMS/service control-plane behavior.
- `terraform-iac` owns HCL/provider/backends/state/import/moved/lifecycle/drift mechanics; this skill owns whether the resulting AWS architecture/service configuration is correct. Many real changes compose both.
- `serverless-platforms` owns Lambda/function handler retries, duplicate delivery, concurrency, cold starts and runtime behavior; this skill owns surrounding AWS account/VPC/IAM/KMS/event-source/logging/quota semantics.
- `finops-cloud-cost` owns allocation, CUR analysis, commitments, rightsizing programs and realized-savings measurement. Cost remains a design constraint here but not the primary optimization discipline.
