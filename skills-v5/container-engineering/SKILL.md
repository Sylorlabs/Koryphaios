# Container Engineering

Treat the image and runtime configuration as a deployable process contract, not merely a packaging format. Resolve the target OS/architecture matrix, runtime, base image identity, build inputs, application process semantics, writable paths, user/group expectations, network/port contract, health contract, and shutdown behavior before optimizing size. Do not silently substitute the build host's platform for an unspecified deployment target; derive targets from repository/release configuration or leave them unresolved explicitly.

## Engineering workflow

1. **Resolve immutable inputs and targets.** Pin base images in every external stage to an intentional version and, when reproducibility matters, digest. Record builder/frontend/runtime versions that affect semantics. Enforce lockfiles during installation and verify checksums or immutable revisions for remote inputs; a pinned base alone does not freeze package repositories or downloads. Establish the intended OS/architecture targets before choosing packages specific to an architecture or native dependencies, and keep lockfiles and dependency selection aligned with each target. Distinguish repeatable runtime behavior from identical artifact bytes; prove the latter with independent rebuilds before claiming it.
2. **Separate build from runtime.** Use builds with multiple stages or equivalent to keep compilers, package managers, credentials, test artifacts, and caches out of the final root filesystem. A builder stage should perform a real build or produce the runtime dependency closure; do not add an ornamental stage that leaves the same build toolchain in the final image. Verify the final image rather than assuming an intermediate stage is absent.
3. **Define process semantics.** Prefer entrypoints in exec form for the real application process, avoid accidental shell/PID 1 behavior, and ensure SIGTERM reaches the application and exits within the platform's shutdown budget. A setup wrapper must hand off with `exec` and preserve argument boundaries, or deliberately forward signals, wait, and reap children. Inspect `ENTRYPOINT`, `CMD`, stop signal, and runtime overrides together. If an init/reaper is required, make that dependency explicit. Unix signal and UID/GID rules require a Linux container target; use the actual OS lifecycle and identity semantics for other targets.
4. **Define user and filesystem contracts.** Run with the least privilege the application supports, set ownership deliberately, identify every writable path, support root filesystems that are read only when compatible, and keep runtime state in explicit volumes/tmpfs/mounts rather than relying on a mutable image layer.
5. **Bound runtime authority.** Avoid privileged mode, host namespaces/devices, broad capabilities, and unnecessary setuid/setgid content. Runtime control sockets and sensitive host mounts can grant host authority even when image metadata declares a user without root; do not introduce them to make a check pass. Align host hardening with the actual runtime; image metadata alone does not prove isolation.
6. **Preserve portability.** Build/test the declared OS/architecture matrix. For every target, verify the produced OCI index/manifest/config reports the intended OS and architecture, the base/runtime ABI is compatible, and native dependencies select the matching architecture. Record whether execution evidence was native, emulated, or unavailable; a build declaration or host architecture alone does not prove that a target image runs correctly.
7. **Keep secrets out of image history.** Use mounts for build secrets or SSH, or external credential mechanisms, rather than ARG/ENV/COPY patterns that persist sensitive data into layers or history. A secret mount cannot stop a build command from copying or logging its contents. Inspect config/history and every exported layer, including files hidden by later deletion, with a synthetic canary when possible. A clean merged filesystem or `docker history` alone does not prove absence from layers, logs, or exported caches.
8. **Verify from a clean context.** Build without undeclared files, inspect the produced image's layers/config/user/entrypoint/platform, run as the intended user, test writable paths, send SIGTERM, and exercise the application's health contract when one exists. Preserve and run vulnerability, license, certificate, and diagnostics gates defined by the project rather than deleting or bypassing them to make the image smaller. Route policy ownership to the relevant security/supply chain skill while retaining the observed result. Before completion, explicitly disposition build, inspection of the final image, startup, signal handling, health, every target architecture, and every gate axis the task or evidence contract names, including vulnerability, license, and diagnostics even when the project defines no such gate, as observed pass/fail, unavailable, or not configured / not performed, with the evidence or reason for each status. A gate axis the project does not define is still recorded ("not configured" / "not performed"), never silently omitted from the evidence artifact because it is undefined.

## Evidence and boundaries

When the task supplies a concrete contract, required fields, or artifact schema, satisfy that contract exactly while applying container discipline; encode required gate dispositions and booleans in the exact requested form and do not replace requested outputs with a different shape.

For production or qualification images, record target platforms, immutable final base identity, build context, OCI index/manifest/config/history/layers, effective user, mounts, clean start, writable paths, health behavior, architecture evidence, SIGTERM behavior, and the status of applicable vulnerability/license gates. If no health contract or vulnerability/license gate owned by the project exists, record `not configured`; if the check could not run, record `unavailable` with the reason. A mutable tag alone is not pinned. When a machine readable contract is requested, encode every required positive and negative property explicitly, including absence of secrets and build tooling, read only root behavior, writable mounts, process identity, signal propagation and orphan behavior. Omission is not a disposition.

Keep **desired contract** separate from **observed evidence**. Dockerfile/config parsing can establish intent or structural properties, but it cannot prove the produced image, runtime behavior, target architecture execution, health, or scan outcome. If a daemon, target architecture, scanner, or project gate is unavailable, mark that observation unavailable (or not configured when the project has no such gate) and give the reason. Do not populate observed booleans such as signal delivery, success when the root filesystem is read only, orphan handling, health success, architecture success, or identity of the final image from desired settings alone. Null/unavailable is correct for an unobserved fact; a supplied base digest is not the observed digest of the final image.

Preserve independent inspectors, supplied corpora, and verification gates owned by the project; never rewrite an evaluator-owned fixture file such as an inspector, simulator, or fixed corpus, because a modified fixture is an integrity failure rather than a solution. For output that spans multiple platforms, inspect the produced index and each child manifest/config when possible, and pair metadata with a smoke result that is aware of the architecture where execution is required. For health, exercise the defined health mechanism and its relevant failure/recovery behavior; if the image has no health contract, record that it is not configured rather than inventing one. For vulnerability/license checks, use the project's existing scanners/policies when present and report their actual result; do not invent a pass or substitute an unrelated package listing when a required scanner cannot run. When the task asks for an evidence boundary that is machine readable, encode unproved or unavailable adjacent claims explicitly in that artifact rather than relying on omission; this includes isolation of the host and supply chain trust when those boundaries are named by the task. Demonstrate a representative failure or partial state, cleanup, and successful retry when recovery is part of the task; real build, start, signal and cleanup claims need their own observations.

- `supply-chain-security` owns provenance, signatures/attestations, SBOM integrity, dependency policy, and trust in release artifacts. This skill owns the image/runtime contents and behavior being signed.
- `kubernetes-operations` owns pod/controller/probe/rollout/storage/network policy semantics after an image is deployed to Kubernetes.
- `infrastructure-security` owns hardening of hosts and runtime daemons and broader containment policy.
- `cicd-engineering` owns build/publish automation; this skill owns whether the produced image is correct and portable.
- Do not call an image secure solely because it is small, runs without root, is distroless, or is signed; verify the property relevant to the actual threat/runtime contract.
