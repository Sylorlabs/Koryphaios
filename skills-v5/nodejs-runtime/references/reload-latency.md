# CPU reloads and latency evidence

Read when the requested fix concerns expensive Node configuration reloads, injected offload callbacks, or event loop latency attributed to CPU work. If CPU profiles show little synchronous work, investigate downstream I/O, waiting queues, and stream backpressure before choosing an executor.

## Locate and move the real cost

1. Capture the supported Node version, module mode, representative config corpus, request concurrency, reload rate, and measurement duration. Use `monitorEventLoopDelay` or an equivalent observer with a CPU profile to locate parse, transform, validation, or serialization work.
2. Trace the caller through any `offload(raw, signal)` dependency. `await`, Promise resolution, timers, and `setImmediate` do not transfer synchronous work away from the calling event loop. An injectable function is a contract until its actual executor is exercised.
3. With measured CPU justification, choose a worker thread, child process, service, or explicitly bounded incremental algorithm. Make the real entry point use it. Account for transfer or serialization overhead, queue capacity, concurrent reload limits, ownership, error propagation, cancellation, and shutdown. Never describe a proposed executor as implemented.

## Publish one complete generation

4. Reject a caller that was already aborted before incrementing the generation or starting the executor. Propagate the exact `signal.reason` when a reload that is still running is cancelled; preserve identity for errors and explicitly supplied reasons such as `null`, and distinguish caller cancellation from an internal shutdown. Give each accepted reload a monotonically increasing generation. Await a fully parsed and validated candidate; commit it only when its generation is still current, the caller has not aborted, and the service is open. Keep the prior complete config visible while work runs and whenever input is malformed, partially written, rejected by the executor, canceled, or stale. Prevent late completion from publishing after shutdown.

## Prove behavior and quantify limits

5. Test concurrent reads during a deferred reload, successful replacement of all fields together, overlapping reloads resolving in both orders, bad input, executor failure and recovery, caller abort, shutdown, and late results. Exercise stream teardown or child spawn/exit only if that path is affected. Observe memory and active handles; check the supported Node majors where relevant.
6. Measure before and after with the same expensive work, input corpus, request traffic, concurrency, and duration. Preserve machine readable latency and event loop results plus the CPU profile or trace behind any reported numbers. A timer that skips parse work, a mocked callback, or synthetic traffic demonstrates only the boundary it actually exercised. Do not infer production p99 or a worker speedup from it.
7. State separately which executor ran, which state transitions passed, and which latency, memory, and resource measurements were captured. Mark missing load, worker, process, and Node version evidence as unavailable. If only the injection contract was repaired, report that partial result and leave performance improvement unverified.

## Keep measured values attached to their run

8. Instrument the **actual** offload invoked by the repaired entry point. For each Worker or process execution, record creation, completion, abort, exit, live resource count, and the observed worker thread ID where applicable; distinguish completed work from stale or rejected results. Account for the whole exercised sequence, including concurrent reloads, cancellation, and shutdown, rather than reporting counters from a separate demonstration with fewer executions. Wait for worker exits before declaring shutdown clean. State whether a duration is worker CPU time or elapsed time; do not silently substitute one for the other.
9. Start the event loop observer before the workload and record its sampling interval, active window, tick count, observed gaps, and wall time. Keep the baseline windows and the windows for the changed path comparable, with real requests running during the expensive work if claiming request latency. Time from request dispatch to completion for request latency; periodic timer gaps are not request samples. A blocked timer can produce **zero samples**; in that case report the relevant percentile as unavailable, not as the workload wall time. Compute percentiles only from actual samples of the named metric and preserve both sample counts and raw measurements.
10. Retain the executed command, Node version, input size or digest, workload and concurrency settings, measurement windows, and the raw observations for each run alongside summary JSON. Check that every reported counter comes from that run and labels the same phase; don't splice worker counts from one test with timing from the event loop of another. An independent checker may exercise a different number of reloads or observation window: investigate the disagreement, report the distinct run provenance, and do not relabel its readings as locally measured values.

11. If the evaluation workspace provides `scripts/collect-evidence.mjs`, use `node scripts/collect-evidence.mjs reload` after repairing the store. It runs the fixture's real native Node Worker sequence and records a report only after the assertions succeed. Keep its `KORY_NODE_RELOAD_PROBE` receipt with the generated report; the independent evaluator will separately execute that sequence against the submitted implementation. Run extra CPU profiles, before/after request measurements, and memory checks when required by the task, clearly separating those samples from the fixture receipt. Do not spend the task budget running unrelated microbenchmarks again to make a counter resemble a different run.
