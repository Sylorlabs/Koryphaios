# Web Security

Reason from the browser security model: origin, site, browsing context, navigation, automatic credential attachment, DOM/HTML parsing, and execution sinks. Automatic escaping in the framework helps only when values stay in the context the framework expects.

## Browser security workflow

1. **Map origins and credentials.** Record scheme/host/port origins, same site relationships, cookies, bearer tokens, embedded/parent windows, origins of trusted third parties, API origins, and which requests automatically carry credentials.
2. **Trace browser sources to execution/navigation sinks.** Inventory URL/query/hash, DOM, storage, postMessage, data rendered by the server, API responses, and content from third parties flowing to HTML/DOM, script, style, URL/navigation, template, and framework escape hatches. **Include requests that change state and are authenticated by cookies in the source to sink inventory itself**: identify form or script input, transformations, HTTP method and endpoint, automatic attachment of session cookies, the mutation on the server side, and the required CSRF and authorization checks. Recording CSRF separately does not account for the input's full path to the protected state change. For cross origin messaging, map both incoming `MessageEvent` data reaching application state and outgoing `postMessage` calls reaching another window. Record the sender/source identity, accepted schema and context, and exact receiver/target origin for each direction.
3. **Prevent XSS at the sink.** Prefer safe DOM/text APIs and framework escaping. Use output encoding appropriate to the context for HTML/attribute/URL contexts and a sanitizer under active maintenance when intentionally accepting HTML. Avoid unsafe HTML/DOM escape hatches unless sanitized and narrowly justified.
4. **Use CSP as defense in depth.** Build a strict policy based on a nonce or a hash, appropriate to the app, with a fresh unpredictable nonce injected into each response and only its matching trusted scripts (or correctly deployed hashes). Remove broad inline/eval allowances and constrain `object-src`, `base-uri`, `form-action`, `connect-src`, and `script-src` for the actual trust map. Distinguish `frame-src` (which children this page can load) from `frame-ancestors` (who may embed this page); a trusted payment iframe does not authorize arbitrary sites to frame the authenticated dashboard. During migration, deploy with reporting only, then verify enforcement including missing/invalid nonces and hostile frame attempts. CSP does not excuse unsafe sinks.
5. **Protect requests that change state from CSRF.** Determine whether credentials are automatically attached. Enumerate every write endpoint authenticated by cookies and pair it with a token that the server validates and binds to the session, an explicit transport (header or form field), and rejection of missing, invalid, or mismatched tokens. Use a synchronizer token, or a token the framework copies from a cookie into a custom header, as appropriate, SameSite as an additional control, and Origin/Fetch Metadata checks where useful. XSS can defeat many CSRF mechanisms, so fix both classes.
6. **Prevent forged requests from the client side.** A hostile URL query/hash can induce a trusted SPA to send a request chosen by an attacker carrying its own cookies, bearer token, or CSRF header even when the API validates tokens correctly. Trace each route or report value controlled by the URL into the eventual `fetch` URL, method, headers, and body. Map untrusted selections to an allowlisted report ID and construct URLs from fixed trusted base origins and route templates; validate parsed origin, allowed path and parameter types after URL resolution. Do not let user input choose an arbitrary endpoint, request method, redirect target, credential destination, or authorization header. Verify a malicious hash cannot select a new origin or privileged API path.
7. **Constrain data shared across origins.** CORS is a policy for sharing an API response, not authentication. For each request that crosses origins, record the caller origin, target origin, credential mode, allowed method and headers, and whether preflight applies. Select an exact origin from a fixed allowlist and send `Vary: Origin` for a dynamic allowlist; reject unknown origins rather than reflecting them, and never combine wildcards with credentials. Validate `postMessage` sender origin, `event.source`, message schema and expected conversation state; send to an exact target origin. Keep origin values as exact scheme/host/port strings in JSON or policy configurations that machines can read (for example, `"https://payments.example.test"`). Do not serialize Markdown links (`"[https://payments.example.test](https://payments.example.test)"`), trailing slashes, URL paths, or other display formatting into origin fields; those strings will fail comparisons that require an exact origin.
8. **Control navigation/framing.** Parse navigation targets against a fixed trusted base and permit only intended paths from the same origin or explicit trusted destinations; guard against URLs that omit the scheme, encoded separators, and redirect chains. Constrain embedding via CSP `frame-ancestors` (and the legacy framing header where required), and reason explicitly about window opener relationships.
9. **Protect cookies and browser storage.** Set Secure/HttpOnly/SameSite/path/domain according to the session model; avoid broad Domain scope. Prefer cookies bound to the host only and the `__Host-` prefix when compatible with the session architecture. Do not put credentials that live for a long time in browser storage merely for convenience when a server/BFF design can avoid exposing them to script. If using a BFF, explain how the browser authenticates to it and protect its routes that change state against CSRF.

## Verification evidence

Produce an explicit origin/credential matrix, inventories of endpoints from source to sink and of endpoints that change state, concrete policies, and test results that compare attacks with legitimate use. In the **source to sink inventory itself**, include one entry for each path that changes state and is authenticated by cookies: untrusted form or script source → validation and construction of the request body → `fetch` or form submission with method and destination → automatic browser cookie attachment → server route and persistent mutation. Name the transport of the session bound CSRF token, origin checks, server rejection behavior, and authorization boundary in that entry; a separate CSRF checklist cannot replace the data flow entry. Verify origin values in machine readable form against the trusted input as exact strings before testing acceptance. Exercise malicious rich text through the actual renderer; nonce failures and frame embedding; missing/wrong CSRF token and hostile Origin/Fetch Metadata; untrusted iframe `postMessage` origins/sources and malformed schemas; URL/hash values controlled by an attacker that try to forge credentialed requests; forbidden CORS origins/preflights; and invalid return paths. Confirm that the legitimate payment iframe, reporting APIs, and session flow still work. Describe observed results separately from planned checks.

## Deliverable fidelity

The supplied evaluator and evidence corpus are read only inputs. Editing either one, or writing a result into its path, is recorded as an integrity failure that no amount of correct behaviour offsets.

Write the deliverable only at the path the task names, in the shape its reader expects. A typed spec is mirrored field for field with every boolean answered rather than omitted.

When the review calls for a source to sink entry for a cookie authenticated mutation, that entry belongs in the inventory even if every other vector already passes, because the inventory is the artifact under judgement.

Write that entry as a structured record with source, transform, sink and control. The source names the session or cookie authentication that makes the request privileged, the sink names the state change, and the control names the CSRF token, its session binding, the server side validation and what the server rejects. Prose next to the record is not read as the record.

## Boundaries

- `application-security` owns broader files, subprocesses, parsers, outbound requests made on the server side, serialization, and trust boundaries outside the browser.
- `secure-authentication` owns authenticator lifecycle and assurance; browser cookies may carry resulting session state but are not the authenticator design itself.
- `oauth-oidc` owns redirect registration, state/nonce, PKCE, issuer/audience, and token protocol checks.
- `authorization-security` owns resource permissions after browser/request identity is established.
- `security-verification` owns final runtime proof of the implemented browser controls.
