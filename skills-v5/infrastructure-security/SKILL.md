# Infrastructure Security

Secure the substrate that runs application workloads. Start from the deployment topology and privilege boundaries, then reduce attack surface, privilege, reachability, mutable state, and unaudited administrative paths while preserving recovery and operability. Treat a manifest, unit file, firewall rule, or policy object as intent until an enforcement result and running state observation show otherwise.

## Hardening workflow

1. **Inventory execution and control planes.** Record hosts/nodes, kernel and OS support status, container runtime and security profile, orchestrator and policy version, namespaces, service accounts, privileged/admin interfaces, images/packages, storage mounts, host devices, ingress/egress paths, secrets mounts, logging/audit path, resource limits, and patch/update ownership.
2. **Start from secure defaults.** Disable or remove unused services, packages, listeners, shells, capabilities, host mounts, privileged containers, runtime sockets, and unauthenticated management endpoints. Treat exceptions as explicit, named, time bounded, reviewable configuration rather than undocumented conventions.
3. **Harden the host boundary.** Keep the kernel, OS, container runtime, and host firewall supported and patched; use a minimal host role; restrict SSH and runtime admin sockets to a management path; and separate host administration from workload identities. On service manager hosts, use a dedicated user without root privileges and applicable filesystem, device, namespace, capability, and resource restrictions rather than relying on the username alone.
4. **Minimize container privilege.** Prefer rootless or user namespaced execution where supported; use a fixed UID/GID that is not root, drop all capabilities before adding a named necessity, enforce `no-new-privileges`, use the runtime's default or an explicitly reviewed seccomp profile plus AppArmor/SELinux where available, and restrict devices, host PID/network/IPC namespaces, `/proc`/`/sys` exposure, runtime sockets, and hostPath/bind mounts. Use a read only root filesystem with narrowly allow listed writable paths and cgroup CPU, memory, PID, and ephemeral storage limits.
5. **Constrain network reachability.** Define ingress and egress by workload/service need rather than broad subnet trust. Establish explicit default-deny ingress and egress intent for every protected workload in the enforcing firewall/CNI, then allow named sources, destinations, protocols, and ports for public traffic, service dependencies, DNS, proxies, and administration. Declare one canonical port map and reuse it in policies, listeners, and probes: do not conflate a public service port, an admin/diagnostics port, a Kubernetes or host control plane port, or a runtime socket. Protect management/control plane ports separately and verify that DNS, IPv4/IPv6, host networking, NAT, proxies, service meshes, and sidecars do not silently bypass the intended policy.
6. **Harden container/orchestrator policy.** Pin an explicit Pod Security Standards level and version appropriate to the cluster release, use enforce mode for the protected namespace, prefer Restricted where workloads support it, and document/exempt only named system components that require broader privilege. Add admission/config checks for `privileged: false`, fixed non-root UID/GID, `allowPrivilegeEscalation: false`, dropped `ALL` capabilities, seccomp and MAC profiles, read only roots, devices, host namespaces/mounts, resource limits, and service account token mounting. Give each workload a purpose specific service account with explicit least privilege Role/RoleBinding (or equivalent) evidence; disable automatic token mounting when it is not needed, and use a short-lived, audience-bound projected token only for a named API dependency.
7. **Patch and recover deliberately.** Maintain supported base images and OS packages, define remediation SLAs by risk and exposure, rebuild rather than mutate live state in immutable images where possible, and retain a named known good rollback artifact and health gate. Emergency changes are narrow, time bounded, audited, and reconciled into managed configuration; verify that rollback restores the intended privilege, reachability, service account/token, and audit posture as well as service health. Artifact provenance/signing remains with `supply-chain-security`.
8. **Protect and observe administration.** Require authenticated, least privileged, time bounded admin access; avoid shared root/admin credentials; log privilege elevation, policy decisions, emergency access use, and configuration changes; and preserve an emergency path whose ownership, expiry, and review are explicit. Do not expose diagnostics or runtime control interfaces through public application ingress.
9. **Verify effective state.** Compare desired IaC/policy with admission/enforcement results and runtime reality: host and workload UID/GID, effective capabilities, seccomp/MAC profile, namespaces, mounts/devices, cgroup limits, listeners, service account identity, policy provider verdicts, reachability, patch/image versions, and audit coverage. An apparently secure manifest, a successful policy apply, or a self reported boolean is not proof of the running configuration.

## Deliverable fidelity

The supplied evaluator and evidence corpus are read only inputs. Editing either one, or writing a result into its path, is recorded as an integrity failure, and no other result offsets it.

When a task declares a typed hardening or isolation specification, write it at the declared path and mirror the declared interface field for field. Nested blocks keep the keys the reader tests, lists keep the list type they declare, and each control is answered explicitly instead of being inferred from a nearby setting.

Distinguish a control the host enforces from a control the document recommends. A stated requirement that no mechanism applies is a gap to report, not a satisfied control.

## Boundaries

For each changed control, record five separate facts: desired value and version, enforcement point and decision, observed running value, an allowed positive control, and a denied negative control. Add a recovery/rollback observation that proves the service returns without restoring the insecure state. Include command/tool, target scope, timestamp or revision, and raw result for identity, reachability, admission, runtime profile, patch, and audit claims. Where only a manifest, simulator, policy compiler, or synthetic matrix is available, label it as design evidence and leave deployment claims unverified; do not fill unavailable observations with `true` or inferred values.

Use these status labels consistently: `observed` means a named provider/runtime returned the raw result; `synthetic` means a supplied fixture or deterministic local check; `design` means intended configuration only; `unavailable` or `unverified` means the live observation was not supplied. A synthetic policy provider row is not an admission receipt, and a planned rollback command is not a rollback result.

Model the administrative ingress source separately from ordinary workload traffic. An application need for dependencies does not authorize access to management endpoints or the cluster/host control plane. Enumerate necessary dependency destinations, protocols, and ports, including DNS and any proxy or patch repository, prove a permitted dependency and DNS path, and test a denied neighbor, public to admin/control plane path, host/runtime socket path, and IPv4/IPv6/proxy/mesh policy bypass path where applicable. Record the enforcing provider and raw result for every probe; a flag claiming explicit egress is insufficient without those concrete paths.

- `cloud-security` owns AWS/GCP/Azure account/project/org IAM, resource policies, provider firewalls/security groups, managed service exposure, cloud KMS integration, workload identity configuration at the provider boundary, and cloud control plane posture. This skill owns the host, runtime, cluster, workload identity, and in cluster network controls that remain after a workload is placed there; compose when a cloud resource and runtime path interact.
- `supply-chain-security` owns dependency/build/provenance/signing/attestation integrity before artifacts reach runtime. This skill consumes an approved immutable artifact reference and checks runtime admission/use, but must not claim that a runtime image reference proves its provenance.
- `application-security` owns in process input, parser, outbound request, file, process, session, and application attack surface hardening. `authorization-security` owns user, tenant, resource, action, and delegation policy; Kubernetes service account and cluster admission boundaries remain infrastructure concerns.
- `secrets-key-management` owns key/secret lifecycle; this skill ensures infrastructure does not overexpose those secrets at runtime.
- `embedded-device-security` owns device secure boot/update/debug/physical lifecycle rather than server/cluster hardening.
- `security-verification` owns independent final evidence and the verdict that deployed controls behave as intended. This skill defines the infrastructure evidence contract and may collect operational observations, but must preserve the handoff and its unavailable gaps.
