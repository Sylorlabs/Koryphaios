# Koryphaios Update System

This document describes how the Koryphaios auto-update system works.

## Overview

Koryphaios uses Tauri's built-in updater plugin. The app checks a `latest.json`
manifest hosted on the GitHub release and, if the version is newer, downloads
the signed installer and restarts.

**Update endpoint (configured in `tauri.conf.json`):**
```
https://github.com/Sylorlabs/Koryphaios/releases/latest/download/latest.json
```

No external server or manual JSON maintenance is required — the manifest is
generated automatically by CI from the build artifacts' `.sig` files.

## How It Works

### Update Check Frequency

- **On launch**: 5 seconds after app starts
- **Periodic**: Every 2 hours while app is running
- **Manual**: Any time via the "Check for Updates" button

### Update Flow

1. App fetches `latest.json` from the GitHub release
2. Tauri compares the manifest's `version` against the installed app version
3. If the manifest version is newer, the update dialog appears
4. User clicks "Install Update" → Tauri downloads the platform-specific installer
5. Tauri verifies the Ed25519/minisign signature against the pubkey in `tauri.conf.json`
6. If valid, the installer runs and the app restarts

### Signature Verification

- Each installer artifact (`.dmg`, `.AppImage`, `.exe`) has a corresponding `.sig` file
- `.sig` files are generated by `tauri build` when `TAURI_SIGNING_PRIVATE_KEY` is set
- The public key is embedded in `tauri.conf.json` (`plugins.updater.pubkey`)
- Tauri rejects any update whose signature doesn't match — no MITM, no tampering

## Release Process

### Automatic (recommended)

Include `/update` in a commit message pushed to `main` or `master`:

```
git commit -m "fix: resolve crash on startup /update"
git push
```

The `auto-release.yml` workflow will:
1. Bump the patch version in `tauri.conf.json`, `Cargo.toml`, `package.json`, `desktop/package.json`
2. Commit the version bump (`[skip ci]` so it doesn't re-trigger)
3. Push a `v*` tag

The tag push triggers `build-desktop.yml` which:
1. Builds Windows, macOS (Intel + ARM + Universal), and Linux installers
2. Signs each artifact (produces `.sig` files)
3. Uploads installers + `.sig` files to the GitHub release
4. Runs the `publish-updater-manifest` job which:
   - Downloads all `.sig` files from the release
   - Maps each to a Tauri platform key (`darwin-aarch64`, `linux-x86_64`, etc.)
   - Generates `latest.json` with real signatures and download URLs
   - Uploads `latest.json` to the release

Once `latest.json` is on the release, all running apps will detect the update
within 2 hours (or on next launch).

### Manual

If you prefer to control the version and tag yourself:

```bash
# 1. Update version in all files
#    - desktop/src-tauri/tauri.conf.json (this is the version the updater compares)
#    - desktop/src-tauri/Cargo.toml
#    - package.json
#    - desktop/package.json

# 2. Commit and tag
git commit -am "release: v0.2.1"
git tag v0.2.1
git push origin v0.2.1

# 3. build-desktop.yml triggers automatically on the v* tag
#    It builds, signs, uploads to the release, and generates latest.json
```

### Required GitHub Secrets

The build workflow needs these secrets configured in the repository:

| Secret | Purpose |
|--------|---------|
| `TAURI_SIGNING_PRIVATE_KEY` | Ed25519/minisign private key for signing update artifacts |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Password for the signing key (if set) |
| `RELAY_URL` | Collaboration relay endpoint (baked into backend at build time) |

If `TAURI_SIGNING_PRIVATE_KEY` is not set, the `.sig` files won't be generated,
`latest.json` will have empty signatures, and Tauri will reject the update.

To generate a signing key pair:
```bash
bun run scripts/generate-updater-keys.ts
# or use tauri's built-in:
cargo tauri signer generate -w ~/.tauri/koryphaios.key
```

Store the private key in GitHub secrets and the public key in `tauri.conf.json`.

## Skipping Updates

To commit changes WITHOUT triggering a release, just don't include `/update`
in the commit message. Only commits with `/update` trigger `auto-release.yml`.

## Files Involved

| File | Purpose |
|------|---------|
| `desktop/src-tauri/tauri.conf.json` | Tauri updater config (endpoint, pubkey, version) |
| `desktop/src-tauri/src/lib.rs` | Rust commands: `check_for_updates`, `install_update` |
| `desktop/src-tauri/capabilities/default.json` | Updater permissions |
| `frontend/src/lib/stores/updater.svelte.ts` | Frontend update logic (auto-check, dialog trigger) |
| `frontend/src/lib/components/UpdateDialog.svelte` | Update notification UI |
| `frontend/src/lib/components/CheckForUpdatesButton.svelte` | Manual check button |
| `.github/workflows/build-desktop.yml` | Builds + signs + uploads to release + generates latest.json |
| `.github/workflows/auto-release.yml` | `/update` trigger: bumps version, pushes tag |
| `homebrew/koryphaios.rb` | Homebrew formula (separate from auto-update) |
| `winget/sylorlabs.koryphaios/*.yaml` | Winget manifest (separate from auto-update) |

## Troubleshooting

### Updates Not Showing

1. Check that a GitHub release exists for the tag (`gh release view v0.2.1`)
2. Check that `latest.json` is attached to the release
3. Check that `latest.json` has a `version` field newer than the installed version
4. Check that the `signature` fields are non-empty (signing key was configured)
5. Check that the `url` fields point to valid release assets (not 404)
6. Check the app console for errors (Ctrl+Right-click → DevTools)

### Manual Check

Users can always check manually via the "Check for Updates" button in the UI.

### Force Update Check in Development

```typescript
import { updater } from "$lib/stores/updater.svelte";
updater.checkForUpdates();
```

### `latest.json` Not Generated

The `publish-updater-manifest` job in `build-desktop.yml` only runs on tag pushes.
If it failed, check:
1. All build jobs (windows, macos, linux) succeeded
2. `.sig` files were uploaded to the release (signing key was set)
3. The `gh release download --pattern "*.sig"` command found files

You can regenerate `latest.json` manually:
```bash
gh release download v0.2.1 --pattern "*.sig" --dir sigs
# Then run the mapping script from the workflow
gh release upload v0.2.1 latest.json --clobber
```
